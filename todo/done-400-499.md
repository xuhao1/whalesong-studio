### 400　理一下审校和修订的逻辑，合理设计一下 ✅（设计；并进 #402）
> 理一下审校和修订的逻辑，合理设计一下

- **现状的毛病**（照第 125 版的代码）：同一章被三个角色各读一遍、各带一套上下文——场记审校（塞前文一大包 + 工具）→ 策划再读一遍定在哪改 → 写手每一处又各带一包（上限 2.4 万 token）→ 采纳后场记再读一遍核对。每条路的上下文规矩不一样；问题卡片上五种修法；找到一个错字也要再跑一趟策划才出提案。
- **设计**：一条流水线，三个角色各干一件事，上下文一个规矩。
  1. **找（场记）**：审校一章时每条问题三选一——改几个字就能了结的，当场写出改法（直接成为提案）；这一章之内要成段写的，说清怎么改、交给写手；牵连别章或要定夺的，只列问题。
  2. **定（策划）**：只在三种时候出场——您说了一句话、问题牵连别章、您点"全书修订"。它每一处照旧判断小的自己写、成段的交写手（#396）。
  3. **写（写手）**：只写成段的文字；交给它的是这一处、前后文、交代它的那位写明的"要守住什么"和文风，不再另拼一包。
  4. **上下文一个规矩**：带工具的每一步，开头只给"手上这一章全文 + 目录"（各章梗概和记忆、人物名单、设定名单、未了线索），别的自己去读；"最多读多少"是一项设置（全局、随书），到了上限就交稿并说明没查到哪里。
  5. **采纳后的核对**：提案对应的问题直接标"已按提案修订"，不调模型；只有引文被这次改动碰到的其它问题才问一次。
  6. **入口**：两个动词不变（审校 / 修订）；问题卡片收成一个"修订"，范围由干活的那位判断，"全书修订 / 整章重写 / 只改引文"收进小三角。
- **分五步做，每步单独量、单独汇报**：① 审校按需读、有上限（就是 #358，并进来）② 审校顺手改 ③ 写手那一处的材料瘦身 ④ 核对改便宜 ⑤ 卡片按钮收拢。
- **要您知道的代价**：① 之后审校查连续性靠各章的"记忆"（收录产生的）和它自己去读；自动收录关着的书，目录里没有记忆，它得多读原文，漏查的风险也高一些——每步做完我拿长书新旧对比找出的问题数和 token。
- 等您说做（或者说哪几步做、哪几步不要）。

### 358　审校一章的上下文太大：设上限；做成 agentic——先由 agent 整理上下文，再审核 ✅（并进 #402 / #403 做了）
> 审校一章每步带 29–50 万 token 的前文，要不要收到固定大小：太大了，需要设置上限，需要agentic来做，放到todo list，由agent首先整理上下文再审核

- 现状（#338 量的）：审校一章的是场记（agent），每一步都带着前文的原文——80 回的测试书里第 41 回约 29 万 token，最后一回约 50 万；它每查一次参考文献、每读一次别的章，这一份就重发一遍。

### 401　审校生成的提案对同样的修改方向有重复 ✅
> 1.现在审校生成的提案对同样的修改方向有重复，是不是提案生成时没有看到过其他提案？

- **是，大部分的路上都看不到**：审校那一步（场记）既看不到已有的问题，也看不到等着的提案，读的是还没改的正文——所以同一个毛病再审一次就再记一条、再出一条提案；而且重审会把旧问题换掉，旧问题名下的提案却还挂着。"照一句话修订"按设计只看现在的正文，同样不知道有提案在等。只有排队的修订看得到"正文带着等着的改动是什么样"，但没人告诉它哪条问题已经有提案了。程序上也没有任何一条规矩拦着两条提案圈同一句话（只拦同一趟里的）。
- 实证（我的测试书）：不同批次的提案圈到同一句话上的有 144 对；第 4 章的审校里同一句引文被记成 3–5 条问题。您的两本加密的书我读不了，没法直接看您那边的实例。

- 修法和实测见 #403 第 ⓪ 步。

### 402　设计审校 / 上下文机制：整章、选取、多章、全篇；列表格说明怎么跑、为什么 ✅
> 2.设计既减少上下文浪费，增加缓存率，又能让模型得到更多的信息，可以减少写作审查的幻觉，执行作者的意图的审校/上下文机制，针对整章，选取，多章，全篇，进行合理的设计，减少重叠的模式。
> 2.你列一个表格，展示设计好的审校，修改等相关功能的运行方式。并解释为什么这么设计既减少上下文浪费，增加缓存率，又能让模型得到更多的信息，可以减少写作审查的幻觉，执行作者的意图

- **设计（10-14 给您讲过，#400 的那一版并进来了）**：
  - **只有两种"趟"**：「章内」——手上一章，找问题，每条三选一（改几个字的当场写出改法 / 这一章里要成段写的交写手 / 牵连别章的只记下）；「跨章」——不带正文，拿各章梗概和这几章已记下的问题，去重、定跨章的矛盾改哪一头，要下结论的地方回原文取证。四种范围都是这两种的组合：选段＝章内只限这一段；整章＝章内一趟；多章＝每章一趟 + 跨章一趟；全篇＝没审过 / 改过的各一趟 + 跨章一趟。不说话是审校，说一句是修订，同一套。
  - **上下文四层，从最稳到最易变，每一趟都这么排**：① 书的底本（文风和您的额外要求、总备注、人物 / 设定名单每条一行、全书章纲、未了线索）② 前情梗概（第 1…N-1 章各一条，只往后追加）③ 手上的正文（这一章全文带段落编号、章纲、出场人物此前的状态、上一章结尾）④ 这一次的事（您的原话、已记下的问题、**等着的提案**、您放弃过的改法、交稿格式）。工具用来取证：读任一章任一段、全书精确查找、读人物卡 / 设定 / 参考文献。
  - **取证规则**：凡说"和前文 / 设定对不上"，必须带出处（哪一章哪句、哪张卡哪一栏），程序去原处核对在不在，不在就退回。梗概只用来找地方。
  - **一处正文只留一条活着的提案**：新提案和等着的提案圈到同一处时，改法一样的不再出，不一样的取代先前那条（先前的进归档）。
  - 谁写：改几个字——找到它的那位；成段——写手，只带这一处、前后文、交办人写明要守住的事实；通篇——整章重写。
- **量过的**（《红楼梦》84 回，正文 61 万字）：各回的"记忆"全文合计 56 万字，和正文一样大（人物状态占三分之二），所以②不能塞整份记忆；各回梗概合计 3.4 万字，是正文的 5.5%。
- **分步做**：⓪ 不出重复提案（#401）① 审校改成四层上下文 + 取证 ② 审校当场改小毛病 ③ 跨章那一趟取代现在的"审校后接着修订" ④ 写手那一处的材料瘦身 ⑤ 采纳后的核对改便宜 ⑥ 问题卡片按钮收拢。每步单独量、单独汇报。
- 等您说做（或哪几步做、哪几步不要）。

### 403　实现审校 / 修订的新方案，同时解决提案时不知道其他提案的问题 ✅
> 实现你说的这个方案，同时解决提案时不知道其他提案的问题。


- 就是 #402 的设计（连同 #401 的修法），⓪→⑥ 都做了。

- **做法**（代码在 `src/core/pipelines/editorial.ts`、`onfile.ts`，`review.ts`、`revise.ts` 改了一大块）：
  - **⓪ 不出重复提案（#401）**：审校和策划开头都看到"已经在案的"——这一章还开着的问题（哪条已有提案在等）、等着确认的提案（原文 → 改成，为哪条问题）、您放弃过的改法；规矩是在案的不重报、放弃过的不再提、等着的提案圈住的句子不再圈。程序上一条硬规矩：一处正文只留一条活着的提案——改法一样的不再出（那条提案同时挂上新的问题），改法不一样的取代先前那条（先前的进归档，放弃新的它会回来）。重审时在案的问题默认都留着；审校说"现在的正文已经没有了"（`gone`）或者它引的那句话已经不在正文里，才标为已处理；同一个问题再报一遍（同一句引文；没有引文时同类、同一出处）沿用原来的编号和它名下的提案。
  - **① 四层上下文 + 取证**：书的底本（文风和您的额外要求、总备注、人物和设定各一行的名单、全书章纲、未了线索）→ 前情梗概（各章一条，只往后加）→ 手上这一章（章纲、出场人物此前的状态、上一章结尾、全文）→ 这一次的事。说"对不上"的问题（连贯、时间线、设定、人物）必须写出对不上的是哪里的哪句话，程序到原处去找：找不到退回重写，退回两次还找不到就不收；没写出处的收下、卡片上标"没附出处"。新工具"全书精确查找"（`book_find`）。"审校、修订时最多读多少"（`context.readTokens`，默认 4 万 token，全局和随书都能设，在设置的"上下文"里，要打开高级选项）。
  - **② 审校当场了结**（审校之后接着修订时）：每条问题三选一——改几个字的它直接写出改法，就是提案（标"场记审校时写的"），不再调模型；这一章里要成段写的，它说清怎么改、要守住什么，交给写手；要动别的章节的标 `wider`，交给策划；该您拿主意的只记下。两条问题不许圈同一处。
  - **③ 策划那一趟**：任务改成稳的在前（底本、前情、相关章节全文）、您的话和问题在最后；带上在案清单；问题的出处在别的章时，那一章也整章带上；问题的出处一起告诉它。
  - **④ 写手那一处**：只拿这一处、前后文和交办人写明的要求（`material: 'place'`），不再另拼一包；策划交给写手时被要求把"要守住的事实、出自哪里"写进交代。
  - **⑤ 采纳之后**：提案名下的问题直接标"按采纳的修订提案改了"，不调模型；同一章里别的问题，只有引文被这次改动碰到的才再核对一次。直接改进正文的（总编改、"多轮迭代"每一轮）也照此了结。
  - **⑥ 界面**：问题卡片一个"修订"按钮（审校写好了改法的直接出提案；牵连别章的交策划；其余照原来的分法），"全书修订 / 只改引文（另写一遍）/ 整章重写"在旁边菜单里；卡片上写出处、"没附出处""牵连别章""改法已写好"；提案卡片标谁写的；修订完的提示写"N 处场记审校时直接改好，M 处交给写手写"；审校引的原话核对不上被丢掉、或读满上限时会提示。

### 419　总编说审校的"条目 id 拿不到（只在工坊界面上）" 🔁
> 现在dsh的会话说对于审校的"条目 id 拿不到（只在工坊界面上）。"，请解决这个问题。解决后发布版本。到libs

- 原因（查了代码）：`novel_review` 和 `novel_read what=review` 回给模型的只有文字，文字里每条问题只写了序号、严重程度、引文和说明，没有问题的 id；id 只在 `data` 里，而 `data` 只给界面、不给模型。可 `novel_revise scope=issues`（`<章>:<问题 id>`）和 `novel_manage action=resolve_issue` 都要 id——总编只能去问您。
- 做法（第 127 版）：
  - **每条问题前面写上它的名字 `<章节 id>:<问题 id>`**（如 `ch003:is_x7k2mq`），修订、标为已解决的工具直接拿它用。`novel_review` 审完的回话、`novel_read what=review ref=…` 读一章的审校都是（`src/core/reading.ts` 的 `issueLine`）。名字后面是状态：开着 / 已解决、您自己发现的、已交去修订、**底下等着的提案 id**、审校已写好改法 / 说清了怎么改、要动别章才能解决、没附出处；再后面是引文、说明、"和哪里对不上"的原话、改法。末尾一句说这个名字给哪几个工具用。场记、策划读审校（`book_read`）也看得到名字，只是不带这一句。
  - **哪几条提案挂在一条问题底下**，原来只在界面（`Issues.tsx` 的 `mendsOf`）；挪到 `src/shared/issues.ts`，界面和工具用同一份。
  - **`novel_read what=review` 不给 `ref`：全书还开着的问题**，一章一节（`## Chapter 3 "…" (ch003): 4 open`），每条一行；默认一次 60 条，`offset` / `limit` 翻页，开头写着一共几条、几章审过。
