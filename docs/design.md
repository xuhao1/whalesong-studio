# Design notes

**English** | [简体中文](./design.zh.md)

Why Novel Studio is shaped the way it is: how a loose list of wishes was folded into a few mechanisms, and what each decision trades away. After reading it you should be able to tell where a new requirement belongs without reading the code first.

## 1. From thirteen wishes to five questions

The starting point was a list: separate the orchestrator from the prose writer; whole-book / outline / local / world / character revision modes; one-click outline and cast from an existing manuscript; ensemble casts with character lifecycles; a world and a persona system; retrieval and long context; style; a UI to manage characters and plot, skim, search and mark what to change; a reading mode and chapters; illustrations; audiobooks; motion comics; a way to step into a scene and role-play it, perhaps as a live visual novel.

Built one by one, these become thirteen features that do not know each other. Grouped by the question each one answers, there are five:

| Question | Wishes | In the design |
|---|---|---|
| **Who writes?** | orchestrator vs writer | five roles: showrunner, writer, architect, analyst, director |
| **What is remembered while writing?** | world, persona, the lives of an ensemble, retrieval / long context, style | one canon + layered memory + a context packer |
| **How is it changed?** | the five revision modes, one-click import | one proposal mechanism at five granularities; import is digest run backwards |
| **How is it seen and handled?** | management UI, reader, chapters, marking | the Studio: a global page and a tab beside the conversation |
| **What can it become?** | illustrations, audiobook, motion comic, role-play / visual novel | the Stage: pipelines that share the audio script as their hub |

The conclusion: these are **not several creative tools but several working modes over one canon**. A mode changes what the showrunner attends to and may touch; the data is always the same data.

## 2. Who does the work: a crew

A book is worked on by a small company: the **showrunner**, who talks with the author; the **writer**, who writes; and four roles that do the rest — **continuity** (场记: digests chapters into memory, reviews them, takes in manuscripts), the **planner** (策划: derives outlines and beats, drafts the bible, explores what-ifs, researches), the **director** (导演: audio scripts, storyboards, interludes) and **post-production** (后期: cuts a chapter's voice, sound and pictures into a video).

**The showrunner is the session's agent.** There is no separate orchestration service: the agent of DSH (DeepSeek Harness) already plans, calls tools, compacts context, tracks todos and asks questions. The plugin ships a preset that gives it the showrunner's instructions, the `novel_*` tools and a project digest that travels with the conversation.

**The writer is a model role, not an agent.** Prose needs no tool loop; it needs a context prepared for this one call and a stable system prompt. So the writer is one model call inside a pipeline: brief in, context packed, model called, output cleaned, text saved, memory digested.

### The other four are agents of DSH

A call is the right shape for work that is one question with one answer. Little of what these four do is that: reviewing a chapter means holding it against the chapters around it and the characters' cards; deriving an outline means reading what is already written, and now and then looking something up; finding the chapters of a scraped manuscript takes looking and trying; cutting a video takes writing a script, running it, looking at the result and correcting it. Where a rule or a single prompt has to guess, an agent can check.

So the four are **not four prompts but four agents**. What sets one role apart from another is exactly this list, and nothing in the machinery:

| | What it is | For example |
|---|---|---|
| Prompt | A persona (who it is) and standing rules (how it works in the crew) | Continuity "records and judges only by what the book actually says" |
| Skills | Guides loaded when the work calls for them, shipped in `crew/<role>/skills/` and listed for that role alone | Post-production's `novel-video-editing`, the planner's `novel-trend-research` |
| Tools | The Studio's: `book_read` / `book_search` to read the book, and the tool this piece of work is handed in with; plus those of the conversation's tools the role's work calls for | The planner has `web_search` / `web_fetch`; post-production has `bash` and file tools |
| Permissions | The permission mode of the conversation that started it, with anything that would need approval refused; the book itself changes only through the Studio's tools | Post-production writes only in its working directory |
| Model | One per role, or the conversation's | Post-production takes the model that codes most reliably |

They run on **DSH's own agent loop**, through DSH's own delegation seam: a role's run is a **subagent**, started through `ctx.subagents` under the conversation that asked for the work, by a provider this plugin registers. What DSH does for every child it then does for a role — the child joins its parent's composition (so the author's own tools, skills and instructions are within its reach), takes its parent's permissions with approval pinned to "never", counts against the delegation depth, and is **entered in the parent's catalog of subagents**: open it from the conversation's header and every step of every run is there, with its tokens and its time. What the provider adds is what makes it *this* role: persona and rules, the Studio's tools, its skills, and which of the conversation's tools it sees. Everything else a loop needs — model requests and their retries, tool calling and argument validation, a durable session log, the token meter, cancellation — is DSH's; the Studio keeps no second copy.

**Work is handed to a role in one of two shapes.**

- *Work with a deliverable* (digest a chapter, review one, derive five, direct a script, cut a storyboard…): the role gets the task and its material, the tools to read the book, whatever of the conversation's tools it may use, and **one tool to hand the result in with**. What it hands in is validated on the spot; what is wrong with it comes back as the tool's failure, and it hands in again. Handing in ends the turn — so where the material is complete, an agent's run is one request, no dearer than a call. Everywhere a pipeline used to "ask a model for a JSON", it now goes this way.
- *A task in words*: the showrunner gives a role a task with `novel_crew` ("research how the Shanghai post worked in the 1930s and propose two scenes for chapter four"); the role reads the book and looks things up, and reports in a paragraph. It does not change the book — what is taken from its report, and how, is for the showrunner and the author.

**Work that has everything in its task is one request.** What an agent is for is that it can look things up in the book. Some work has nothing to look up: cutting a chapter into an audio script, digesting a chapter, laying a storyboard over a script, fitting a prompt to what a model reads, sorting the notes an author jotted down, telling a life in a paragraph from what the digests noted, learning a style from samples, looking at open issues again after a revision, laying the foundation of a new book, parting a book into volumes from its chapters' summaries — all of it is in the task. Such work is one plain call whatever its role is set to (`Assignment.plain`): a set of tools and a dozen steps would only add to every request what it has no use for, and room to wander. Whatever reads the text or the bible — a review, the cast, ties, signature scenes, growth, deriving chapters — is an agent as before.

**When it is not an agent, that is said.** A role can be set to plain calls under *Settings → Crew* (one question, one answer: faster and cheaper, and blind to the rest of the book); and when an agent hands nothing in, or cannot run at all, the same work falls back on one plain call. Both are written on the job — who worked, in which way, in how many steps, and why — never done quietly.

**How many tools a role has is the author's call.** By default a role has its own tools and those few of the conversation's that its work calls for. *Settings → Crew* can open "all of DSH's tools" for a role — whatever the conversation has (a shell, files, the web, MCP…) — except, always, the showrunner's own `novel_*` tools and the ones that need a person in the room (questions, goals, further delegation). These settings apply to every book, or travel with one.

**Outside help.** When post-production cannot cut a video well itself, it may hand the work to another agent that writes code. That is not a wheel the Studio reinvents but DSH's own subagent: with `@deepseek-ai/dsh-subagent-claude-code` or `@deepseek-ai/dsh-subagent-codex` installed, the rows of `@deepseek-ai/dsh-tool-subagent` already mounted in the preset turn `subagent_claude_code` / `subagent_codex` into tools; without them, those rows do nothing.

The tools carry the guard rails, because a tool can check what a prompt can only ask for. Taking in a manuscript: a cleaning pattern that would delete a fifth of the book is refused; a pattern that backtracks without end is cut off after three seconds; "titles" that read like sentences are told apart by the numbering, and the report carries the correction ready to copy; a run out of steps leaves its soundest split behind. Cutting a video: a result is taken only if it passes the checks — a picture, a sound that is not silence, a length that matches the telling, no long black stretches — and a path outside the working directory cannot be handed in. Every run has a budget of tool calls; once it is spent, only the tools that close the work still answer.

Why do text models come only from DSH? Because the agent loop takes DSH's models and no others. A Studio that connected other vendors' text endpoints itself got roles that could not be agents, and models to configure in two places. So every text model comes from DSH's *Settings → Models* — connect whichever vendor there — and the Studio configures only what is its own: the models that draw, speak and search. (A role saved with an endpoint of its own by an earlier version keeps working, by plain calls only; the Settings screen says so.)

The roles take separate models because their demands conflict: the **planner** must reason and diverge (outlines, bible development), **continuity** must be fast, literal and attentive (digest, review), the **director** must be quick and keep to a format (scripts, storyboards, and you wait for it on every move of an interlude), **post-production** must code reliably. Unset roles fall back (planner → writer; director → writer or continuity) and finally to the conversation's model. "One model for everything" and "the best model for each step" are two ends of the same setting.

What is not an agent yet: the writer (by design — see above); a turn of an interlude, which is still one call of the director's — you wait for it on every move, and an interlude is itself one continuous conversation, so the shape it wants is one standing director agent per interlude, which is the next step; and the small one-line-in, one-line-out jobs (an illustration's prompt, a style sample).

The showrunner is told not to *write* manuscript prose itself: prose that bypasses the writer's pipeline bypasses the bible, the characters' current states, the style. But a conversation is full of changes that are not writing — the author dictates a sentence, pastes a paragraph of their own, wants a name put right — and routing those through a model that rewrites is slow, costs money and is not exact. So the showrunner has hands of its own for exactly that (`novel_edit`: replace, insert, append, delete, set), and uses them when the words are the author's, when the change is mechanical, or when the author asks it, in so many words, to write something itself.

### One road for every change

The first version drew the line between the showrunner and the book by prohibition: use the tools, do not touch the files. Used for real, that left the showrunner with too little it could do directly — and nothing stopped it from reaching for a raw file tool when its own tools did not fit, changing a chapter with no version kept and with memory still describing the old text. The author's words for it: the main agent "偷偷暗改", out of step with memory and the bible.

The answer is not more prohibition but one road, wide enough for everything:

- **Every kind of change has a tool**, and each tool does the bookkeeping: the text as it was becomes a version, the chapter's memory is digested again, search is re-indexed, and the result tells the showrunner where the change leads — the cards of the characters it names, the chapters written after it. What memory records wrongly can be corrected directly (`novel_memory`) rather than by hoping a second digest reads better.
- **The road around is closed, gently.** A raw `write` or `edit` (or a shell redirect) aimed at a book's own files is refused with the name of the tool that does the same thing properly. It is the author's setting, not the showrunner's, and can be loosened to "ask me" or "let it through".
- **What gets around anyway is seen.** The Studio tells its own writes from anyone else's by the state of the file, not by timing; a chapter changed by an editor, a script or a tool that was let through goes on the record and is digested again, and the showrunner's context says that it happened.
- **Nothing changes the book unseen.** The overview carries the book's record — what the showrunner did with its tools, what was done from another device, what changed from outside — with one-press undo for manuscript edits.

This is what "agent-native" comes to here: the conversation can do everything the screens can, and what it does is as visible and as reversible as what a hand does on a screen.

## 3. What is remembered

**A book is a directory.** Markdown for what a human writes, JSON for structure and machine memory, so the author can open their book in any editor, version it with git, and the agent's file tools can read it when needed. All writes go through one locked project object that also watches the directory, so outside edits show up live.

**Personas.** Beside the biography, a character card has a structured persona: traits with intensity, values in priority order, speech habits, lines never crossed, behaviour under pressure. Its purpose is concrete: voices blur in an ensemble when cards hold only adjectives; the writer needs executable constraints. The same card carries the character's appearance, design sheet and voice. Consistency of looks and voice does not rely on model memory — every call restates the same appearance and sends the same reference picture or clip (see *One look per book* below).

**A life, not a label.** A card carries no status. It once did — planned, active, offstage, retired, dead: one word for where somebody stands in the book — and the word was taken away, because a book is not one straight road. It has lines of the plot that part, and chapters written again long after the ones that follow them; "dead" holds on one line from one chapter on, and written on a card it is wrong on every other line and in every earlier chapter — and all it speaks of is how far the story has got.

**Who is worth a card is the planner's to say, once it has looked.** A digest notes everybody a chapter meets, the doorman as much as the rival. Each new name used to become a "new character" suggestion, and a long book buried its cast under a hundred of them. A digest proposes nobody now: every name without a card is on the list of walk-ons (read off the digests, so none is lost), and once a batch of chapters has been digested the planner looks through the names it has not looked at yet, side by side and against the book, and says of each what it is — **worth a card** (a suggestion, with its reason and how large a part), **another name** of somebody (a suggestion to fold it in), or a **walk-on** (left on the list, with why). The judgement is the planner's; there is no threshold of appearances. Unsure of somebody seen once, it leaves them a walk-on, and is asked again when they are seen in more chapters. Nothing is done for the author: a card and a folding-in are suggestions, and a walk-on can be given a card by hand at any time. What an older version proposed chapter by chapter is looked through in the same pass. The pass after digests can be switched off; the button stays.

Where somebody is in the book is a record: where they come on, the chapters they are in, where they are away, come back, leave or die. That record needs no keeping of its own: every chapter's digest already notes who was in the chapter, what they went through, how they stood at its end, and whether they came on, left, came back or died there; laid out along a line of the plot those notes are the life, and so it is always what the text says. Laid out along another line it is another life: somebody dead on one line is alive on the one that parted earlier. Beside it a card has the life told in a paragraph — continuity's to write from the digests, the author's to edit.

A digest misses things and gets things wrong, and there are things no digest can see — somebody dead before the first page. So the author can write a **mark** of their own: comes on, comes back, leaves or dies at a chapter, or was dead or gone before the story begins. It is still no label: it is an event of the life, with its chapter — it holds on every line of the plot that chapter is read on and on no other — and it holds over what the digest says of that chapter. After a death or a leaving the author wrote down, later chapters that have the person only remember them; to bring them back, the author writes a return.

What the writer sees follows from it, for the chapter in hand and along that chapter's own line: everyone's card, the same whatever the chapter (so the head of the request does not change from chapter to chapter, and a provider's cache holds) — leads and supporting parts whole, the rest a line each; for the people of the scene, their state after their last chapter and a line of theirs from the text; and a list of who is out of the story *as of the chapters before this one* — the dead, who may be mentioned and must not appear alive, and those gone for good, who do not come back unless the outline brings them. Somebody who dies in chapter 16 is alive to whoever writes chapter 5 again. Presence is computed from digests as well, so "who has been away for ten chapters" is a fact, not a recollection. In the Studio everyone's life stands in one table (People → Lives): a row a person, a column a chapter, read along the chosen line.

**Layered memory.** After each chapter the analyst extracts a one-line brief and a summary; hard facts; each character's state, place, mood, what they learned and a representative line; entities new to the bible; threads planted, advanced and paid off; the reader's open questions. Every ten chapters roll into an arc summary. Far-away story is coarse, recent story is fine, the last pages are verbatim. Memory carries a hash of the text it came from, so edited prose shows as undigested.

**Context packing — an outline of what came before, and a window of the text itself.** The story before a chapter is given in two layers. *The text*: the whole chapters closest to this one, verbatim and in order, within a budget that defaults to half of what the model can read (500,000 tokens for a model that reads a million; a figure of your own if you set one). Whole chapters only — a chapter that does not fit is left out, never cut. *The outline*: one line per chapter for everything older (ten chapters roll into an arc summary further back), with the plan's own summary standing in for a chapter that was never digested, so no written chapter is ever simply absent. While the manuscript fits, the outline layer is empty and this is "the whole book"; once it does not, near is verbatim, far is summarised, and retrieval only fetches a few passages back out of the far part. The window comes from the role's own figure, DSH, the endpoint or a table of common model families; a model nobody can place is taken to read 200,000.

*What follows is given too.* Rewriting or revising a chapter in the middle of a book, the chapters already written after it go in as well — nearest first, whole chapters, summaries for what does not fit — with the instruction that this chapter must lead into them, not contradict them and not use up what they are about to tell. The text before keeps priority; the text after keeps at least three tenths.

*The order is built for the provider's prefix cache.* A request is two blocks. The first does not depend on the chapter: book, core world, the whole cast (full cards for the leads, a line for the rest), the outline of what came before, the text. Writing the next chapter, that block only grows at its **end** by the chapter just written. The second belongs to this call alone: the text that follows, the present state of the people in this chapter, open threads, relevant lore, retrieved passages, the chapter ahead, the chapter so far, this chapter's plan, the brief and the length. Three things keep the first block still: the writer's system prompt no longer carries the length or "you are continuing"; the heading of the text says where it starts, not where it ends; and the window does **not slide by a chapter at a time** — it holds its starting chapter until the text no longer fits, lets go of the oldest quarter at once, and holds again. So nearly every chapter of a writing run is "the last request plus one chapter", and what the provider reports as read from its cache is recorded in the ledger and shown with the result.

Retrieval is hybrid: BM25 over CJK bigrams and Latin words, optional embeddings, fused by reciprocal rank. "Retrieval only" (the cheapest) and "fill the window" can still be forced in the settings.

**Length is a budget you may give — or not.** A chapter can carry a recommended length, in its plan or as a figure for the whole book; the writer is told "about N, give or take 15 %". **Give none and the writer judges**: it is told that no length is set — write each beat of the plan out fully, without padding or hurry — and how long the chapters already written run on average. New books are no longer stamped with "3,000 words a chapter", and the 3,000 (2,500 in English) nobody chose on older books no longer counts. The showrunner is told that length is the author's to give and not to invent one.

**The plot graph — a story may go more than one way.** The volumes of the outline are the **main line**: the book as it is read, exported, voiced and staged. Beside it there can be other **plot lines** — another way things could go that the planner derived, a stretch that was played in an interlude, the plan that was there before the outline was rewritten. A line **leaves** after a chapter, may carry the choice made at the fork, and may **join** another line at one of its chapters; so the plot is a graph, drawn as one under *Outline → Plot graph*.

- *Rewriting the outline asks what becomes of the old one.* Deriving chapters can start after any chapter and either append, **replace** what followed, or **open a line** so both ways stand. Replacing loses nothing written: if any replaced chapter has text, the stretch is kept as a shelved line that can be found and made the main line again; only chapters with no text are dropped.
- *Lines can be handled.* Rename one, state its choice, join it to another line, shelve it, remove it — or **make it the main line**: the chapters it runs through become the book's order, and the stretch of main line it replaces becomes a line of its own, leaving and joining at the right places.
- *Choosing a line at the next chapter.* The Write view lists one line at a time (what it shares with others is dimmed) and switches between them; after a chapter where the story forks it asks which way to write next. The showrunner asks the author in the same situation.
- *A line's chapters are chapters.* Written, digested, reviewed and staged like any other, with "what came before" being the line's own reading order. One difference: **what happens on a side line stays there** — someone who dies on a side line is not dead in the book. Cards and the main threads follow the main line; a line's memories are folded into the bible when it is made the main line.
- *The plot is a graph, and it can be re-wired by hand.* A chapter — or a run of them — moves elsewhere on its line, onto another line, or onto a line opened for it (a name, and the chapter it leaves after; none makes it a story of its own from the first page): a side story imported among the main line's chapters is parted from it so. One dialog does it, and the plot graph, the outline and the writing page all open that one. A chapter is found by its id, so its text and whatever was made from it go where it goes; lines that leave after it or arrive at it follow. A move that would tie a line into a knot — a line leaving after one of its own chapters, a way round in a circle — is not made at all, and is not offered. Where a line leaves can be said again at any time, in the line's own dialog.
- *A line reads itself.* A book may hold several stories that are apart from their first page and share one world. So whoever works on a line — the writer of its chapters, a role deriving, reviewing or staging them — is handed, and can read with its own tools, **that line** and nothing of the others: its text and digests, its people, its threads, and the world the lines share. Another line is another story as far as that work goes. Every line counts its own chapters (a line that parts counts on from where it parts); "chapter 3" read by a role is that line's third. Whose a character is needs no marking: as the card says where it says, else where they are — in a line's chapters by their digests, or cast by their plans — and a card no chapter has yet is every line's. The bible's entries are the world the lines share until they are filed — not guessed from where the text happens to spell a name out, since an entry the whole book stands on may be named on one line only. Three ways file them. The digest that finds a thing says whose it is as it reads the chapter — in a book of several lines it is told which story the chapter is of, and answers of each new thing whether it is that story's alone or the world's; a thing of the story alone is filed, when its suggestion is taken up, under the lines that read the chapter (its own, and whichever part from it later — when that is every line, under none), and is not handed to the others. Where a digest did not say, a thing found beside the main line is that line's and one found on the main line the world's. The author files a batch at once; or the Studio files a batch by the text (what every line has, or none yet, is left). The bible's pages list the line in hand: its own above, what the lines share in a group of its own, and what is filed under none on its own. A thread is the lines' that planted or advanced it, and one paid off on the main line still waits on a line that parted before. The book's premise is the main line's: a line apart from the first page is told by its own name and what the author said it is about. What crosses over is named: somebody a chapter's plan or the task itself names is given whichever line they are of, and what happened on another line is the showrunner's to read (it is kept to no line) and to pass on in its brief. Who a name is goes by the story too: a line that parts from another tells that one's story on, a line apart from the first page is another story, and a name in a chapter is somebody of that chapter's story. A narrator's "我" is a different person in every story; a proper name borne by a card of another story is the digest's to judge — come over, or a namesake — and whoever is told apart is kept under the name with their story after it. *Whose card a digest's note on somebody is, one place says* (`whose`, from `Project.castResolver`), and every reading of a digest asks it — who is on a line, a life, the walk-ons, the cast a digest fills into an empty plan, the pointing of digests at cards after a cast is consolidated. What a digest settled as it read the chapter stands (it says so on the note: `by`). An older digest left an id only — and an id is made of the name: it holds within the stories its card is of, and in another story the note goes by its name again, as that story has it. Which stories a card is of is told by what does not go by a name: the lines the author filed it under, the chapter it first appeared in, the plan of a chapter not digested yet. So two stories' narrators, mothers and bosses that an earlier "a name is whoever bears it, anywhere in the book" put on one card are told apart *as they are read* — the book is not to be digested again for it — and the one that is not the card's is, in its own story, a walk-on without a card. On the bible's pages a line shows what is filed under it, then what the lines share (what its story names, or no text names yet), and last, folded, what is filed under none while only other stories' text names it — theirs in all but the filing, with one press to file it by the text.
- *An interlude can become a line*, not only a chapter: it leaves after the chapter it was played from, the session is its first chapter and the player's first move is the choice.
- *Reading follows a line too*, and at the end of a chapter where the story forks the reader is offered the ways on, each labelled with its choice. That is the step towards a story one can choose through: the graph, the choices and the chapters on each way are already data.

**Style** is its own object: point of view, tense, tone, diction, rhythm, imagery, dialogue, rules, a "never" list, sample passages. The "never" list does the most work. Styles can be learned from a sample, tried on a test scene, and switched per book.

## 4. How it is changed

| The author's mode | What happens |
|---|---|
| derive the outline | the architect reads memory and threads and proposes chapters, beats or what-if branches; you review before anything enters the outline |
| local revision | select a passage → the writer rewrites only that, with its surroundings as context → a proposal |
| chapter revision | the writer rewrites one chapter to an instruction → a proposal |
| whole-book revision | the architect triages which chapters are affected, the writer changes only those, one proposal per chapter, grouped as a batch |
| world / character revision | change the bible first, then start a whole-book revision that carries the change through |
| mend what a review found | one: the writer rewrites the quoted place. A batch: tick several issues (across chapters), say a word on each, and the planner reads them side by side, settles which chapters change and how — also chapters nobody named that tell of the same thing — and each is rewritten once; or hand over every issue from a severity up in one click. Once proposals are accepted, the reviewer reads what is still open against the text as it now stands: what the change settled is marked, what reads differently is brought up to date. **Mendings do not lock each other out**: another can be asked for while one runs, and a small triangle beside the button says how it is taken — **in line** (the default) after the ones before it, going on from the changes they leave waiting, so that they agree; **apart** at once and by itself, for mendings that have nothing to do with each other (another line, a far part of the story) |

Shared rules: changes are **proposals** with a diff (revisions started in the Studio always; the showrunner's apply directly unless you ask to review them); the previous text is **snapshotted** before anything applies; a passage proposal goes **stale** when its target text has since changed — better that than pasting a rewrite in the wrong place; mutating tools **ask first** in read-only sessions.

### Translation: the names first, then chapter by chapter

Hand a model a book of several hundred thousand words a chapter at a time, and the first thing to break is not the prose but the **names**: one person is Shen Heng in chapter three and Shen Hang in chapter forty; one thing has two renderings. A model does not remember, so nothing is left to its memory:

- **A glossary is what a translation goes by** (`bible/glossary.json`, one a language): people's names and what they are called, places, houses and organisations, things, the book's own words — one rendering each.
- **Settled first, translated after.** Where the book has cards, continuity settles the names off them — **who somebody is decides how their name and their forms of address come out** (a man or a woman; a nickname or a name). A book with no cards yet (a manuscript just brought in) has its proper names found in the text. What is settled stands: every pass only adds.
- **A chapter is sent with the terms it uses**, each with what it is — not with the whole glossary. A translator (the writer model) that meets a name without a rendering settles one and hands it back; it is added, and later chapters go by it.
- **Afterwards the cards learn their names**: the rendering becomes another name the card goes by. The digests, the marks on names in the text, the context of the next chapter all tell people by a card's names — so Shen Heng in the translation is still 沈蘅.
- **The author has the last word**: the glossary is read and corrected in the translate dialog; what they set is marked theirs, and no later pass writes over it. A name rendered badly is corrected in the glossary, not in a chapter.
- **The translation takes the text's place and the original is kept**: as a version of the chapter (*before it was translated*); the chapter says *From …* beside its title, and its menu puts the original back, title and all. A picture's path in the text is not touched.
- **Two ways in**: *Translate…* in a chapter's menu on the writing page (this chapter, or every written chapter of the line; a long chapter goes stretch by stretch, each in the voice the one before ends in; several chapters at a time), and *The manuscript is in* on the import form — a manuscript in another language is translated into the book's as it comes in, and digested, carded and outlined from the translation.
- When every written chapter is in the language, it is the book's language (what it was is kept on record).

### What was changed is kept: versions of everything written

A chapter's text always had versions; a character card, an entry of the bible, a style, a chapter's plan, a thread, the book's own info had none — the showrunner changed a card, the director rewrote an appearance, a field was cleared by a slip, and how it was before was gone. They now keep versions one way:

- **A version is the thing before a change**, named by when and by what changed it: the author, the showrunner, a job by its name ("before *Writing the appearance* changed it"), a version put back, a deletion. One is kept only when what the thing *says* changes — not for a picture, not for what the Studio keeps by itself (first and last appearance, where a chapter stands), not for a save that changes nothing.
- **A sitting of the author's own edits keeps one**: the thing as it was before the sitting, not one for every press of Save. What somebody else — the showrunner, a job — made of it in between is kept all the same.
- **Pictures are no part of it.** A picture stays for as long as nobody deletes it; a version put back leaves the card with the pictures it has now. A version is about words.
- **What is shown is the difference, and one field can be put back alone.** *History* lists the versions; beside them, every field in which the one chosen differs from the thing as it is now, as a diff — the whole version goes back, or one field of it. What the thing was until then is kept first, so putting back can be undone.
- **What was deleted can be had back.** A card, an entry, a style is kept as it last was when it is deleted; *Deleted…* at the foot of its list restores it — or removes it for good.
- **One control, the same everywhere** it applies: people, entries, styles, the art direction, a chapter's plan, threads, the book's info — and the showrunner reads the same record (`novel_manage action=history / restore_history`).

**Import** is digest run backwards: split chapters → digest each → merge character moments into cards and entities into world entries → rebuild the outline and threads from the summaries → learn the style. It reuses the everyday memory pipeline, so an imported book is indistinguishable from one written here.

## 5. How it is seen and handled

One component tree, two doors: a **page** in the left sidebar (the bookshelf, no session needed) and a **tab** in a session's right sidebar. The tab is where the integration lives: when the showrunner calls the writer, the chapter streams into the editor beside the conversation; a selection can be rewritten directly or handed to the conversation with its chapter reference; each `novel_*` call in the transcript reads as "which model was asked to do what" and opens the Studio at that place.

Principles that run through the eight views (overview; people — everyone's card together with the table of lives, the relationship graph and the walk-ons, so that whatever is about people is on one page; bible — world, prose style, art direction; outline; write; read; review; stage):

- tell the author the next step — the overview is a to-do list, not a dashboard;
- selection is the entry point to change — not "enter a mode, then find the place";
- model output is a suggestion by default — bible suggestions, revision proposals, derived plans all wait for a yes;
- long work is visible and stoppable — and stopping a draft keeps what was written when that overwrites nothing;
- narrow rooms are first-class — layouts follow the container's width, because the tab is often 450 px wide.

### One click, and many at once

Doing a thing to one chapter is a button; doing it to fifty by pressing fifty buttons is a punishment. Whatever is "the same thing for many chapters, people or places" is therefore **one job**:

- **Stage → Produce**: a table of every chapter's progress (script, voice, sound, storyboard, pictures, video); tick the steps and the chapters and press once. When a chapter's script is set, its voice, its sound and its storyboard go on together; pictures follow the storyboard; the video is cut when all of it is there. Several chapters move down the line at once, the first started finishing first.
- **Write → Write a run**: chapter after chapter — beats derived where there are none, each chapter digested before the next begins, so every chapter has read what the last one just wrote. Without writing, beats, digests and reviews run for many chapters at once.
- **Gallery → Draw a batch**: design sheets and place sheets first; portraits, chapter illustrations and the cover wait for them and are drawn from them; each character's own voice can be made in the same go.
- One chapter has its one click too: "Make the audiobook" (script + voice + sound) on the audio page, "Produce this chapter" (everything) on the comic page.

Three rules hold for every batch. **Only what is missing**: each step looks for work before starting, so a batch that was stopped, or that had failures, is finished by running it again. **A failure breaks only what depends on it**: the steps of that chapter that needed the failed one do not start; every other chapter goes on, and the job ends with a list of what was not made and why. **All of it is visible**: every step of every chapter is a cell of one live table, and the agents' runs are listed under the conversation as always. The showrunner does the same with `novel_batch`.

**Concurrency is something else, and it lives in one place.** How many requests are out at once is not decided per job but by four gates — speech, pictures, sound, text — each counting everything that uses it, whichever chapter or job it belongs to. The default is 8, the ceiling 256, both in the settings. When a service answers "too fast" the gate slows itself (halves, pauses), sends the refused requests again instead of dropping them, and climbs back a step at a time once things go through — saying so on screen while it lasts ("speech is being rate-limited: 8 → 4"). The figure can therefore be set high without fear: the real limit is the account's quota at that service, and it is found by running into it, not guessed.

### Conversation first; screens for seeing and fine-tuning

This is an agent-native application, so the most direct way to use it is not to click through screens but to talk to the showrunner in a session. Three rules follow:

- **Whatever a screen can do, the conversation can do.** Every operation behind a screen has a tool, including the settings (`novel_settings`: read and change the model roles, run a one-click setup, edit the book's own information) and the small hand edits (`novel_manage`: restore a version, change a line of the audio script or a panel of the storyboard, settle a review issue…). A screen is not the only door to a feature; it is where a person **sees, checks and fine-tunes**.
- **The showrunner can show you a screen.** `novel_show` opens a screen, a chapter or a tab of the stage in the author's window — "show me the outline" opens it rather than describing where to click. The Studio appears beside the conversation the first time the showrunner goes to work; after that, keeping it open is the author's call.
- **Full screen is the host's.** The right sidebar already has a full-screen mode; the Studio only puts the same switch in its own header, closer to where the author is looking. No overlay of its own, hence no second copy of the state.

The one thing that does not go through the conversation is a key: the showrunner neither takes nor repeats one; it opens the settings and lets the author paste it.

### One conversation, one book in play

A workspace holds several books; a conversation and the Studio beside it must not each have their own idea of which one is meant. So there is one fact — **the book in play of a session** — and both sides read and write it.

- *Changing book in the Studio moves the conversation.* The alternative, a panel that can look at one book while the showrunner works on another, makes every "write the next chapter" ambiguous. Looking is switching; the Studio says so when it happens.
- *The showrunner must be told, durably.* The Harness turns a changed runtime context into a message in the conversation's own history, so the switch is on record where the earlier turns are: which book is in play now, which one the turns before were about, and that leftovers of the earlier book are to be finished by naming it, not carried across. It survives compaction because it is restated with every digest.
- *A call acts on the book its model was last told about* — not on whatever is in play at the instant it runs. An author who opens another book while the showrunner is mid-step has not redirected the calls it already decided on; the next step tells it, and it decides anew.
- *An agent at work for a conversation is on the book that work is about* — never on whatever book its folder happens to be. A role's run, or a subagent the showrunner sends out, is a new conversation handed its parent's folder; and a folder can be a book of its own with other books inside it (the first book made in an empty workspace becomes the folder, the next ones go inside). So for a child the folder is asked last: first the book its task names, then the book of the conversation it works for. Asked first, the folder put the Studio beside a scribe at work on the inner book onto the outer one, and told a helper the wrong book was in play.
- *Several books in one conversation remain possible* — by naming, not by guessing. Every tool takes an optional `book`; the row in the transcript shows it; once a conversation has been on more than one book, every result says which book it is about. Reaching outside the conversation's workspace to change a book asks first.

### Nothing fails quietly

Most buttons start a job and return. A job nobody waits on that fails must still reach the author, least of all silently when the cause is that something was never set up. Two rules: the ending of every job this Studio saw start is reported; and a failure that means "not set up" — no speech model, no key, a subscription not signed in — is not an error message but a prompt with the way forward (one-click setup, or the settings opened at the right section). Long jobs say what they are doing: voicing a chapter shows the lines done, the line in the booth, time taken and time left.

The same goes for the half-second scale. A button that starts work shows itself working, in words, until the work ends; and one bar at the foot of the Studio lists everything in progress for the book — requests the Host has not answered yet, and running jobs whoever started them — with what each is doing, for how long, and a way to stop it. A click that seems to do nothing is a bug, whatever the code behind it was doing.

And for degraded results. A step that could not do its job properly and fell back on something lesser — a passage of an audio script cut by rule because the model's reply was cut off — writes that into what it produced, with the reason, and the screen shows it. The Studio also sets no cap of its own on how long a model's reply may run: a model that reasons spends its reasoning out of the same allowance, and a cap sized for the answer silently truncates it. That one mistake had produced scripts without speakers and storyboards of two panels, both looking like finished work.

### What is looked at is made like a beautiful game

It is called a writing tool, and it is at least as much a thing for an author to enjoy their own work in: turning the pages of a cast, of a world, is a pleasure of its own. So looking good is a requirement here, not a finish. Every page that is for looking — reading, listening, the motion comic, people, places and things, the world, the home page — is held to the standard of a beautiful game: large pictures, the picture first wherever there is one, somewhere to step into and wander (from a city to a house to a person), movement where it helps — not tables and forms. Nothing of the editing is taken away; it sits behind *Edit* and *Produce*: what is there otherwise is the finished thing, and the tools come when there is work to do. The looking and the changing of one thing are two faces of one address, a step apart from either side.

**The viewer is one application, used in three places.** What a reader is given — the text (read, heard, watched as a motion comic), the people, the world — is one set of pages (`client/reader/`) fed by answers made in one place (`core/reader.ts`). It stands in the Studio's navigation as *View*, it is the page other devices are served, and it is what a published site consists of. So nothing looks one way in the Studio and another once it is out. The three differ in two things only: the author's own viewer also shows who and what the text has not come to yet (a plan, which a reader is not given), and on the author's side every page has *Edit* at its top right, a step to where that thing is made, with *View* on that page a step back. Of a card a reader is given what a collection of settings prints; what somebody wants and lacks, the change planned for them, their secrets, the notes, and how they are written, drawn and voiced stay with the author.

### Connecting models: one click, or slot by slot

Setup serves two kinds of people. **Those who would rather not study it**: the first time the Studio opens with nothing configured, it opens on a guide — pick a service, paste one key, click once, and writing, images, speech and retrieval are set as recommended; the key is checked against the service first, and a refused key changes nothing. **Those who want to decide**: every slot (four roles, images, speech, retrieval) names its own service, endpoint, key, model and reasoning level; a text role may use a model configured in the Harness or point straight at any OpenAI-compatible endpoint.

Keys are kept **per endpoint host**, one record each, in the Harness credential store. Several capabilities of one service therefore need the key once — and a key only ever travels to the host it was entered for: moving a slot's address elsewhere does not carry the key along.

**What is recommended is data, and it is published.** Models move faster than code is released: the image model a service is best used with, the models worth offering beside a field, the window of a model family all age by the month. None of it is in the code; it is `recommended.json`, an issue with a number and a date that goes out with every version. An author's settings follow it as far as the author wants: a setting that still is what an issue recommended moves to what the next one recommends, a setting the author chose is never touched, and whatever moved is said — with the old and the new value, and a way to take it back. An author who does not follow is told what an issue would change, and nothing is changed. Nothing about a model being superseded is ever done in silence.

**The settings page starts short.** Two models to choose — the writer's, and one for the crew — and one line each for pictures, speech, sound and retrieval. Everything a role can be told beyond its model lives on that role's own block under *Advanced*: its way of working, its tools and its steps are not a second table somewhere else on the page.

A ChatGPT subscription is the odd one out: it can draw, but it has no API key. The Studio adds no sign-in of its own and rides on one that exists — the image service the Codex Connect plugin exposes to companion plugins, or a Codex CLI already signed in on the machine. A subscription has no embedding or speech endpoint, and the Studio says so instead of pretending.

### What the interface says: what a thing is, and no more

A hint answers the question the author has at that spot: what this is, what happens on a click. It does not tell how things work behind it, does not repeat what the button beside it says, and adds no aside in brackets. A hint is one short sentence at most and none where none is needed; a tooltip is a phrase; a confirmation says what will happen and whether it can be undone. The mechanics are in the documents. The measure for new screens: an explanation the author would do without is not there.

## 6. What it can become

Five things share one model, with the **audio script** as the hub:

```
manuscript ──director──▶ audio script (per line: narration/dialogue/thought, speaker, delivery;
                │                       per scene: ambience)
                ├── speech ──▶ audio drama   (a clip per line, one voice per character)
                └── director ──▶ storyboard ──pictures──▶ motion comic (a panel per few lines + a camera move)
                                                              │
                              voice + sound + pictures ──post-production──▶ video (one MP4)
```

- **Audio drama.** A speaker's voice is resolved in a fixed order: the voice on the card → a voice designed for them → a voice cast by gender and age. What is cast is written into the book's voice sheet and read from it ever after, so casting does not depend on who happens to speak first in a chapter, and speakers without a card get a lasting voice too. Clips are cached by a hash of provider, voice, direction and text, so editing three lines re-renders three lines. Speech providers implement one small interface.
- **Listening without ears.** A generative speech model does not always do what it was asked: a line comes back in another voice, cut short, or twice as loud as its neighbour — and it is at its least steady on lines of a few syllables. The pipeline therefore measures every take (duration against the words, level, median pitch against the voice's reference clip or its own long lines), takes a failing line again, keeps the best take, marks what still stands out, and brings every kept line to one level. The script helps from its side: narration is kept whole rather than chopped into fragments, and delivery notes are not reinvented on every line. None of this needs another model, and none of it claims more than it measures: a syllable says more about its tone than about its speaker, so very short lines are not judged on pitch.
- **Ambience** uses no model: the browser synthesizes it with Web Audio — filtered noise as the bed, slow modulation for breath, scheduled one-shots (thunder, crackle, drips, crickets). The script only says "this scene is a rainy night".
- **Motion comic.** The script is cut into beats — a short line whole, a long one sentence by sentence — and the storyboard director arranges beats into panels, so a panel may change in the middle of half a minute of narration. How many panels is the author's call (a density that names how long a picture stays, or `auto`, and a ceiling that always holds), because every panel is a picture to pay for. The chapter is boarded a window at a time; a director that stops early is asked for the rest instead of having its last panel stretched over everything left. Prompts include each character's appearance and the book's art direction, and each panel is drawn against the design sheets of the people in it; playback follows the lines with slow camera moves.

- **Video.** The motion comic is put together by the Studio as it plays; the video is a file, and it is **not assembled by rule**. What the chapter already has — a voice for every line, sound cues, a picture for every panel — is material: the Studio lays it out on one timeline (every line's start and end, every panel's, every cue's moment), in the forms a shell takes easily as well (one voice track already aligned, subtitles cut for the screen, tables of panels and cues, a base script that makes a plain first cut), and hands it to the **post-production agent**. How to cut it is the agent's business: it reads the material, finds out what this computer's ffmpeg can do, writes its own script, runs it, checks, corrects — and calls in outside help when the work is beyond it. What the Studio keeps for itself is the judging: a picture, a sound that is not silence, a length that matches the telling, no long black stretches, the lines where a viewer gets them; only then is the file taken. Subtitles show where that line runs: the Studio gives the lines cut and timed, says the viewer must see them, and checks that they are in the picture or carried as a track — and writes no tool to put them there. The first time a cut came back with its words only as a track (this computer's ffmpeg draws no text), the tempting fix was a small native program of the Studio's own that draws them. The author refused it on two counts that are now rules: **work an agent can do is not done for it by a deterministic helper** — material, a clear ask and a check are the Studio's part, the commands are the agent's; and **the plugin is bound to no system while an agent is bound by nothing** — the plugin runs wherever DSH runs and so carries no code of one system, whereas an agent at work faces exactly one computer and may use anything that computer has.

### Enter sends a form — not the Enter that takes a word from an input method

Chinese, Japanese and Korean are typed through an input method, and the Enter that picks a candidate reaches a text field as a key like any other. Every field that goes on Enter (changing a picture, a brief for the writer, how a passage should change, a new person…) goes on a plain Enter only (`plainEnter`), or its author's sentence would leave half typed. A new field of the kind uses the same check.

### One page to read and to listen

The audio drama used to be a tab on the stage, away from the reader. But listening is reading by ear: it is the same chapter, and what a listener wants on screen is the text, not a table of takes. So the reader is where a chapter is heard — and, since the motion comic is the same chapter over the same script, where it is watched. It has three faces (the prose, the script line by line, the comic) and one player under the first two: listening is not a mode but a button, and the chapter is at the same place whichever face is open. Over the prose each script line is located in it (lines ignore paragraph breaks and dialogue has lost its quotation marks, so the match leaves white space out and falls back on how a line begins and ends), the sentence being spoken is lit, and any sentence starts playback. The author's tools — make, check and repair, export, the tools on every line of the script — are on the same page instead of on another screen, but not in the way: they come when *Produce* is pressed, and what is there otherwise is what a reader would have.

The same page is what a phone gets. A reader served to other devices cannot be the Harness (which stays on its machine, behind its own authentication), so the plugin runs a small server of its own for it: off until switched on for a book, read-only by construction (there is no route that writes or reaches a model, a key or an unshared book), and addressed by a random token that can be replaced. It is assembled from the very components the Studio's reader uses, so the two cannot drift apart.

### One look per book, and none of it hidden

Two things go wrong when a book is illustrated one prompt at a time. Words mean something else to an image model — a story's "church" becomes a cathedral, "white armour" a crusader — and a model that has never seen a character draws a new person each time. And the fixes tend to be hidden: a style phrase appended behind the author's back decides the look of a whole book without ever being shown.

So the look of a book is made of parts the author can read, and every picture records which parts it was made of:

- an **art direction** per book, and only per book: a noir of the 1920s and a space opera are not painted alike, so the look is a page of the book's bible, not a setting of the Studio. The director settles it from the book itself — its period and place, the temper of its prose, its leads — when a manuscript is imported and when a bible is drafted, and again whenever the author asks. A book from before this, with none of its own, starts from the built-in direction (or the one once entered Studio-wide), and its first picture writes that text into the book, where it is shown with its origin and can be changed. A default that shapes everything is a default that must be on record;
- **avoid lists** — per Studio, book, character and call — for what the setting does not have. They go to the image model as the negative prompt and to the model that writes scene descriptions, which is also told to replace loaded proper nouns with what the thing actually looks like;
- one **appearance** per character — and nothing beside it. The writer writes the person by it and every picture of them is drawn by it. There used to be a second text, a *visual anchor* written for image models alone; two texts of one thing drift apart, so it is gone (a card that still has one is drawn from it, as before, until it is folded into the appearance — the director writes one paragraph, the anchor holding where the two differ — or the author rewrites the appearance or drops it). An appearance is a paragraph of prose in the book's language, of what can be seen; where somebody stands and what is behind them is not their appearance — written into it, it turns up in every picture of them. It is written with the art direction in hand. An art direction can say more than how to paint — "dress and buildings of the Ming" — and appended after a subject it only colours what the subject already said: an appearance that follows the novel's own words to "one thick queue" is drawn with a queue under any art direction. So the period and the forms the author settled belong *in the appearance*, and whoever writes it is told they hold over the source text — the form replaced, not blended, and what is the person's own carried onto it;
- **design sheets**: the same person from the front, the side and the back, sent with every later picture of them as a reference image. Outfits are *looks* with sheets derived from the main one — the same face in other clothes — and places have reference art of their own.

The order matters and the Studio says so: direction and avoid list, then appearances and sheets, then pictures.

*A portrait is not an identity photograph.* Asked for with nothing said of it, it shows the person in the moment a reader remembers them by — and which moment that is cannot be computed: it is a judgement about the book, so the director makes it, reading the text, and writes it onto the card where the author can overrule it. The Studio's part is the frame around that judgement: what a portrait is (this person as its subject, one instant held still), that the choice is said and kept, and that nothing is picked where the book has nothing yet. Two things follow from its being a judgement. What the author asks of a portrait — brighter, the night of the fire — is *guidance to whoever judges*, not a replacement for the judging: the director picks the moment that answers to it. And which moments are fit to be shown is not the Studio's to decide by kind: a book's Christ is on the cross and its general in the thick of the fight; the author says what their book does not show, on its avoid list or in what they ask. (A first version listed kinds of moment never to pick. It kept the director from a boy's love scene, and from the crucifixion with it.)

*Signature scenes are a list in plain sight, not a decision made out of it.* The director finds not one moment but several, and they sit on the card by weight: which moment, which chapter, the picture, why it is theirs. The author sees them, rewrites them and chooses among them before anything is drawn — which is why nobody is stopped to be asked first.

*Words lead, pictures follow.* A reference picture is the strongest thing a prompt carries: told to match one, an image model returns it. So which way references run is a decision, and it runs one way only — from the words to the sheet, from the sheet to everything else. The main sheet is drawn from the appearance and the art direction alone, never against an older picture of the person: a sheet held against the sheet before could not change, whatever the author changed, and nothing on the screen would say why. A portrait, a scene, a panel are held against the sheet; a look against the main sheet, with the prompt saying what the reference is for (the face, not the clothes). To change how somebody looks, change the words and draw the sheet again — then what was drawn against the old one says so. And a prompt speaks of a reference only where one goes. How many a service takes is the service's to say — a server of the author's own in its model list (`reference_images.max_count`), OpenRouter in its listing, ComfyUI by having a workflow for them — and never the Studio's to tell from a model's name: a server learns to take pictures, and a guess that it does not outlives the day it was true. Where the service says, the prompt is written for that many and what stayed behind is kept with the picture; where nothing says, the pictures are sent, and a service that will not have them is asked for the picture again from the words alone — the prompt written anew, with not a word of any picture — with what it answered kept on the record. "Match your reference" with no reference behind it is an instruction about nothing, paid for out of what room the prompt has. And what a service did not take is said *after* the picture is there, with the picture — never before, as a warning about a picture not yet drawn: what was true of a service an hour ago is not a thing to tell the author, and what happened to this picture is. Which of a person's two pictures leads is the author's choice (`image.lead`): the design sheet (words → sheet → portrait and the rest), the portrait (words → portrait → sheet → the rest; such a portrait is never drawn against the sheet), or neither. That is the standing choice; beside the two buttons on a person's page each picture has its own — *the portrait from: the sheet / the words alone*, *the sheet from: the portrait / the words alone* — which starts out as the setting has it and holds for what is drawn from that page (`from`, on the request). The way from a portrait the author likes to a sheet that matches it is then one choice away, where the pictures are, whichever of the two leads. Whichever it is, the line runs one way, and nothing already drawn is redrawn because what it was held against changed — the page says which has fallen behind, and the author redraws it.

*A picture is a picture, whichever page drew it.* A panel of a motion comic is on record, in the gallery and in the same viewer as a portrait or a scene; and any picture the book has can be placed after any paragraph of its text — from the picture (*Place in the text…*) or from a passage selected on the writing page. Nothing is drawn for that; the text changes at that one spot.

*A design sheet goes along as its front view.* Handed all three figures of a sheet, an image model draws three people, and words do not talk it out of it (tried); so every picture but a sheet itself is held against the first figure, cut out of the sheet.

*A panel's prompt has two halves.* The director writes what happens in the frame and names who is in it, what they wear there and which things it shows; how each of those looks is put after the director's words by the Studio when the panel is drawn — from the bible as it stands, in full, never as a storyboard once abridged it.

*One control for a picture, wherever one is shown.* Opened large — from the gallery, a person's page, an entry of the bible — a picture has its record beside it and, under it, what can be done with a picture, the same everywhere: keep a copy; *rewrite its words and draw it again* (the art direction, what it kept out and the references it had go along as before); *change one thing in it* (the image model gets the picture and the author's words for what to change, and nothing else — the picture already says what it shows, in what manner, and what has no place in it; said again in words that would only lengthen the prompt. It keeps the frame the picture has. Only where the image service takes no picture do the picture's words stand in for it, the change after them, and the record says the picture stayed behind. What the picture shows in words is kept on its record, unsent, for when its words are rewritten later); take it out of the book. The viewer does not close when a picture has been drawn again: it stays where it is and shows the one that came of it (its author asked for the change to look at it, and as likely as not wants another); while it is drawn, the form stays put. The picture drawn again takes the old one's place wherever that hangs — a design sheet, a look, a stretch of a life, the portrait of a moment, an entry's art, the cover — and the old one stays in the gallery; portraits are kept side by side, the newest first as the face, for the author to order and to thin out. A picture taken away is let go of in all those places. A house or an organisation has design art as a place or a thing has: the one picture that stands for it.

*A picture can be traced.* "Every picture records its parts" is worth what the author can do with it when a picture comes out wrong. Opened large, a picture is shown with its record beside it: the parts of its prompt in the order they were sent and where each is changed, the reference pictures that went with it — each opening its own record, so a look can be followed back from picture to picture —, the words the image model got, exactly, and how all of it stands against the book as it is now (an appearance or an art direction changed since; a portrait drawn against a sheet that has been drawn again). A braid nobody asked for is then a word in the appearance, a picture that was sent along, or the model's own habit — and the author can tell which without asking anyone.

**One brief for every picture.** Every prompt is laid out the same way — a line a part under its name, in one order: what the picture is for, the picture, its framing, the people, the place, the things, what was asked of this one, the art direction, the reference pictures by number, what must not appear. It is what the makers of the image models most used here ask for, and it reads the same to a strong model and a weak one, so there is one layout and no strategy per service. The brief goes as it is; the director writes it out only where it does not fit the model, or where the author has every prompt written. Somebody whose picture goes along is pointed to ("see Image 1") rather than described again — a look restated beside a moment in other clothes pulls the picture back to the look — and the words not sent are kept on the picture's record, for when it is drawn again where no picture can go.

**A portrait is a pair, and what stands for a moment is chosen.** Asked for with nothing said, a portrait is a plain likeness (the person's face, standing where they first come on) and their signature scene (standing where the chapter tells it); where the two places are the same or near, the scene alone stands there. A moment drawn more than once lists every picture of it, and the author says which is the moment's. Which moment a picture is of is read off the picture's own record — never off a note beside the moment, which a chapter digested again, a comparison or an older card can lose.

**The picture of a passage is an agent's to frame.** Who "she" is, where they are, what is in their hands is known only from the text before and the bible: the director reads, names the people, the place and the things, and writes the picture; the Studio lays the brief out from that.

**Design art is kept side by side too.** The art of a place, a house or a thing follows the rule of the design sheets: drawn again, the picture before stays on the entry — one is the *main picture* (what pictures that show it are held against, and what stands for it in the lists and the viewer), the rest are kept without being in use; ones drawn to compare and not taken, and earlier ones the gallery still has, are in the same row on the entry's page. Which is the main one is the author's to say; once chosen, a picture drawn after waits, and with no choice made the newest is the main one; where the main one is deleted, the one behind it is next.

**What is asked of one picture is worked into its prompt, not put after it.** A sentence the author adds to a design sheet or a plain likeness ("a cane in the right hand", "a snowy night, no glasses") used to be one more line of the brief — under a line that said "arms at the sides". The director, who writes prompts, now works it in, in one plain call: each part it speaks of is changed — the pose in the picture (a sheet has no such part: in the half of the framing that says how they stand), weather and light in the surroundings, what is worn in *wearing now* — and what the brief said against it goes; somebody pointed to by a reference picture and asked to differ from it has that said in their line. No other part is touched. A portrait of a moment does not take this step: there what the author asked already went into choosing and framing the moment. Where the author has prompts sent as laid out (`promptWrite: 'never'`), the line stays a line.

**A moment is framed before it is drawn.** A signature scene on a card is told as a story is told — "she puts the draft into the brazier" — and drawn from that, an image model knows neither what she wears at that point nor what is around her, while the telling is full of words that cannot be drawn. So the director, as an agent, reads the paragraphs of the chapter that tell the moment and frames it: the action in a short sentence, what she wears *then* (by the text; her usual clothes where it says nothing), the surroundings, who and what is there with her. The frame is kept on the moment and used while the moment's words stand; the brief of the portrait is purpose → the picture (that sentence) → surroundings → framing → the person (by their sheet) → what they wear now. A brief holds what is in the picture and nothing addressed to the model about how to read it. Where the director cannot be had the moment is drawn as told, and the result says so.

**Every button that draws offers several models.** Portraits, sheets, design art, the cover, the picture of a passage, panels, a new picture in the gallery, batches, one-click production: one small button, one dialog — several image services (or several models of one), a picture each, side by side, and nothing counts until one is taken; a picture taken lands where a plain draw would have put it (on the card, the entry, the panel, after the passage). Many pictures at once — a chapter's panels, a batch of portraits — are a *round*: taken whole by service, or one by one under *Stage → Illustrations → Waiting to be taken*.

**A picture may come from outside.** Beside the buttons that draw a portrait or a design sheet — of a person, a stretch of their life, an outfit, one of their moments — is *Import*: a picture from the computer is hung and recorded like one that was drawn (marked as imported — it has no prompt, so nothing to redraw from).

**References can be changed for a redraw.** Under the two fields of *Rewrite the prompt and redraw* are the reference pictures the picture went with: any can be taken away, others added from the book or the computer; the numbers the prompt points by and its line on references follow, and somebody whose picture was taken away is written out in words.

**The pictures of a chapter show where it is written.** Beside the editor is a list of the pictures the chapter's text carries, in order, each with the sentence before it: moved up or down, moved to after the paragraph the caret is in, taken out (the picture stays in the gallery), or another put in from the gallery. It edits the line in the text — saved and versioned like any edit. Portraits placed by rule are not in the text and are not listed here.

**Rewriting a prompt means the whole prompt.** What the author rewrites to draw a picture again is everything the model was sent — with its art direction and its line on the reference pictures — and, apart from it, everything that was kept out; what goes again is those two fields, to the letter.

### References: other books to go by, read by the crew

A book may go by other books — a book of the shelf, consulted as it is organised there and as far as the author opens it; or a manuscript taken in for this book alone, as plain text (to have it organised first, it is imported as a book of the shelf: no half-organised middle is built here). Nothing of a reference is put into a task whole: the crew reads in them with tools kept to what is open, with the author's line on how to go by each. The writer has no tools, so the planner reads for a chapter before it is written and leaves notes on its plan, which the author sees and corrects; where the planner cannot run as an agent, that is said — notes are never made up.

How a reference is gone by is the author's to say, in their own words, at two levels: one line **for all of them** — which book for the world, which for the way of writing, whether people may be borrowed — said to everybody who works with the references at hand, and one line for each. Both hold; where they are at odds, a reference's own wins.

Whether to look is not left to a role's guess. A role that has the tools need not use them: "look where the work touches them" hands the model the question of whether it does, and a model that thinks not never looks. So three kinds of work **look first**: writing (the planner's notes, above), deriving (chapters, beats, a what-if) and reviewing. A derivation and a review are told to, and what they hand in is not taken until they have read or searched in a reference — sent back twice at most, so that a role that will not look is not kept from handing in for ever. What was read is counted off the calls the role made, not off what it says of itself, and is in the result. Each kind can be turned off, which leaves it to the role again; a role that works in plain calls has no tools to look with, and the result says so. A review is also handed the notes the chapter's writer was given, and files what is at odds with the references as issues.

### Interludes, and why this is not a role-play front end

In a role-play tool the chat is the product and the story a by-product. Here it is the reverse: the story is the product and playing is a way to probe it — rehearse a confrontation before writing it, or try the branch where she never left.

So an interlude is a fork off the canon. It is anchored after a chapter, and the director knows the canon only up to there. You play one character or direct from outside ("someone knocks"). Each turn the director returns narration, lines with actions, optional choices, scene changes (place, time, mood, ambience) and the variables it tracks. The Studio presents it as a visual novel — background, portrait, dialogue box, choices, voice, ambience — with pictures and speech generated on demand. When it ends it is discarded, kept as a side story, or **novelized**: the writer turns the transcript into a chapter in the book's style. Only the last changes the canon, and that chapter is digested like any other.

### What it costs

Staging is where the money goes, and a writer's model at a million tokens of context is not free either. The Studio keeps a ledger of every model call it makes — tokens per role, pictures, seconds of speech — and adds it up by model, role, book and day. It counts and does not guess prices: money appears for the models the author has priced, in the currency they entered, and an unpriced model is reported as unpriced. The showrunner's own turns belong to the Harness's count and are named as the one thing the ledger leaves out.

## 7. Fitting into the Harness

- **One npm package, three entry points**: Host (project, pipelines, jobs, API), agent (tools, prompt, command — mounted inside the preset), browser (the Studio). It ships its own configuration patch.
- **Official seams only.** Text model calls go through DSH's model runtime, so every route under *Settings → Models* works; roles run as agents through `ctx.subagents` (the plugin registers a provider of its own); outside help is DSH's own `dsh-tool-subagent`; keys go through the credential store; UI registers through slots; browser and Host talk over the Harness connection, so Web and Desktop behave the same.
- **What the Harness gives its agent, a plugin's own calls do not get.** Retrying a failed request is done by `dsh-llm-retry` on the agent loop; a call made through `ctx.llm.stream` gets the first failure as the last. The Studio therefore runs the provider's retry policy itself for the calls that are still calls, and moves work that is more than a call onto the agent loop, where none of this needs a second implementation.
- **Two prompt layers.** A fixed description of the division of labour sits in the system prompt (cache-friendly); the project digest and the working mode are dynamic context, re-sent only when they change.
- **Working mode is session state** — ideate, bible, outline, draft, revise, review, stage, play — switched in the Studio or by the showrunner.

### Sealed books

A book is plain files so that anything can read it; a sealed book is one its author does not want read by anything — a backup, a sync service, whoever opens the folder. Encrypting "the manuscript" would not be enough: a portrait, a voiced line, a memory digest, the name of a character's file say as much. So sealing is done underneath everything else: every read and write of a book goes through one small interface, and a sealed book's implementation of it encrypts content and names alike. The rest of the code neither knows nor cares.

**The conversations about the book are sealed with it.** DSH keeps every conversation as a log on disk, readable by whoever reads the disk, and a conversation with the showrunner about a book contains the book: the chapters it read, the plot the author talked through, what each agent looked up. DSH has no call to encrypt or delete a conversation, so the Studio **takes them away** when the book is locked: each log is encrypted into the Studio's own directory and the plain copy is removed from DSH's session store (with the title and summary DSH had derived from it); unlocking puts them back as they were, and the conversation can go on. "About the book" means: conversations bound to it, conversations in which a showrunner tool touched it, the runs of the agents that worked on it, and every child of those. So that a conversation can be put away while the book is **locked** — one that was still open at the moment of locking has to wait until it is closed — a sealed book's `novel.json` carries a public key that only takes in: anyone can add, only the book's key takes out. A conversation in use is never pulled from under DSH; it is sealed once DSH lets go of it, at the latest when DSH next starts. The plain copy is removed only after the encrypted one is on disk (and, when the key is at hand, opened and compared).

The book's key is random and exists unwrapped only in the memory of a running Harness. On disk it is wrapped once per way of opening the book — a password, a computer's own unlock, a device that showed the password once — in the one file that stays readable. Presence is asked of the operating system (Touch ID, Windows Hello, the computer's password) through the script host the system comes with — `osascript` on a Mac, PowerShell on Windows — by a few lines that answer yes or no and hold no secret; the secret they gate sits in the account's credential store. Nothing is compiled or shipped for it: the plugin is the same files wherever DSH runs, and where a system offers no such check (Linux, for now) a book opens with its password. DSH itself has no owner check a plugin could call — its desktop shell exposes none, and a page of the shell cannot use WebAuthn, which browsers keep to https and localhost — or the Studio would use that. The showrunner is on the outside of all of this by design: it can lock a book, never unlock one, and a password is never typed into a conversation.

## 8. Deliberately not done

Collaborative editing (one author per book); bundled models or keys; calling a video-generation model (a chapter's video is cut by the post-production agent from voice and pictures that already exist; the motion comic is a moving storyboard); a rich-text editor (chapters must stay plain text you can open anywhere); encryption in transit for the reader on other devices (it is plain HTTP inside the local network, and says so — a certificate a phone trusts is not something a plugin can conjure).
