# 设计说明

[English](./design.md) | **简体中文**

这份文档解释小说工坊为什么长成现在这个样子：最初的那些零散想法是怎样被归并的，每个关键决定在取舍什么。读完它，你应该能判断一个新需求该落在哪一层，而不必先读完代码。

## 一、从十三条想法到五个问题

最初的想法大致是这样一张清单：编排器与写手分离；全文修改 / 大纲推演 / 局部修改 / 世界观修改 / 人物修改；从已有稿件一键生成大纲与人物；群像与角色生命周期；世界观与人格系统；RAG 与长上下文；文风；管理人物与剧情、看梗概、翻阅查找、圈定修改的界面；阅读模式与章节；插图；有声小说；有声漫；可以临时下场的角色扮演，甚至实时 Galgame。

逐条实现会得到十三个互不相识的功能。把它们按"在回答什么问题"重新归类，只有五个：

| 问题 | 对应的想法 | 落到设计里 |
|---|---|---|
| **谁来写？** | 编排器与写手分离 | 五个角色：总编、写手、架构、分析、导演 |
| **写的时候记得什么？** | 世界观、人格、群像的履历、RAG / 长上下文、文风 | 一个正史 + 分层记忆 + 上下文打包器 |
| **怎么改？** | 五种修改模式、一键导入 | 同一套"提案"机制下的五种粒度；导入是"反向"的收录 |
| **怎么看、怎么动手？** | 管理界面、阅读模式、章节、圈定修改 | 工坊：既是全局页面，也是会话旁的标签页 |
| **写完还能变成什么？** | 插图、有声小说、有声漫、角色扮演 / Galgame | "演出"：以有声脚本为枢纽的一组流水线 |

结论是：那些想法**不是多个创作工具，而是同一个正史上的多种工作模式**。模式只改变总编此刻的关注点和可以动什么，数据永远只有一份。

## 二、谁来写：一个剧组

一本书由一个小班子来做：和你对话的**总编**，执笔的**写手**，以及四个各管一摊的角色——**场记**（收录记忆、审校、整理导入的书稿）、**策划**（推演大纲与节拍、起草设定、假设分支、查资料）、**导演**（有声脚本、分镜、幕间）、**后期**（把配音、音效和分镜画面剪成视频）。

**总编就是会话里的 Agent。** 没有另起一个"编排服务"：DSH（DeepSeek Harness）的 Agent 已经有规划、工具调用、上下文压缩、待办、提问这些能力，再造一遍没有意义。插件提供一个预设（小说家 Novelist），给它总编的人格说明、`novel_*` 工具和随对话携带的项目摘要。

**写手是一个模型角色，不是一个 Agent。** 写正文不需要工具循环，需要的是一份为这一次调用精心准备的上下文和一个稳定的系统提示。所以写手是"流水线里的一次模型调用"：总编（或你在界面上）给出简报，流水线打包上下文、调用写手模型、清洗输出、保存、收录记忆。

### 其余四个角色都是 DSH 的 agent

"一问一答"适合一个问题一个答案的活。可是场记、策划、导演、后期的活大多不是这样：审一章要对照前后章和人物卡，推演大纲要翻已经写下的东西、有时还要上网查资料，找一份扒来的书稿的章节要一边看一边试，剪一段视频要写脚本、跑、看结果、再改。规则和单次提示只能猜；agent 可以去查证。

所以这四个角色**不是四段提示词，而是四个 agent**。一个角色和另一个角色的区别，恰好是这张清单，机制上别无不同：

| | 是什么 | 例子 |
|---|---|---|
| 提示词 | 一份人设（它是谁）和一份守则（它在剧组里怎么干活） | 场记"只依据书里实际写了什么来记录和判断" |
| skill | 用到时才加载的做法，随包发布在 `crew/<角色>/skills/` 里，只有这个角色的目录里有 | 后期的 `novel-video-editing`、策划的 `novel-trend-research` |
| 工具 | 工坊给它的：查书的 `book_read` / `book_search`，这件活的交回工具；以及对话里的工具中它的活用得上的那几样 | 策划有 `web_search` / `web_fetch`，后期有 `bash`、读写文件 |
| 权限 | 继承发起它的那场对话的权限模式，需要批准的操作一律拒绝；书稿本身只能通过工坊的工具改 | 后期只能往它的工作目录里写 |
| 模型 | 每个角色单独指定，或跟随对话模型 | 后期选写代码最稳的 |

它们跑在 **DSH 自己的 agent loop** 上，而且走的是 DSH 官方的委派接缝：一次角色运行是一个 **subagent**，通过 `ctx.subagents` 在发起它的那场对话之下启动，provider 由本插件注册。于是 DSH 为每个子 agent 做的事，对角色也一样做了：加入父对话的组合（作者自己的工具、skill、指令因此都在它够得着的地方）、继承父对话的权限并把"需要批准"钉成"拒绝"、计入委派深度、**登记在父对话的子智能体目录里**——在对话标题栏点开就能看到每一次运行的每一步，token 和用时都在。provider 只补上让它成为"这个角色"的东西：人设与守则、工坊给的工具、它的 skill，以及对话里的工具它能看到哪些。循环需要的其余一切——模型请求与重试、工具调用与参数校验、持久的会话日志、token 计量、取消——都是 DSH 的，工坊没有第二份实现。

**把活交给角色有两种形状。**

- *有交付物的活*（收录一章、审一章、推演五章、编一段脚本、切一段分镜……）：角色拿到任务和材料、查书的工具、它能用的对话工具，和**一个交回工具**。交上来的东西当场校验，不合格的原因作为工具的失败返回给它，它改了再交；交回即结束这一轮——所以材料齐全时，一次 agent 运行就是一次请求，不比单次调用贵。原来流水线里"向模型要一个 JSON"的地方，现在全部走这条路。
- *用话说的活*：总编用 `novel_crew` 把一件事交给某个角色（"查一查民国上海的邮政，给第四章想两个桥段"），角色自己查书、查资料，最后用一段话汇报。它不改书——采纳什么、怎么落到书里，由总编和作者决定。

**不走 agent 的时候要说出来。** 每个角色可以在"设置 → 班底"里改成"普通调用"（一问一答，快而省，但看不到书里别处）；agent 没交回结果、或者根本跑不起来时，同一件活会退回一次普通调用——这两种情况都写在这次任务的记录里（谁、以哪种方式、几步、为什么），不会悄悄发生。

**给多少工具由作者定。** 默认每个角色只有自己的工具，加上它的活用得上的那几样对话工具。在"设置 → 班底"里可以给某个角色打开"DSH 的全部工具"——对话里装了什么它就有什么（命令行、文件、联网、MCP……），只是永远拿不到总编自己的 `novel_*` 工具和需要人在场的工具（提问、目标、再委派）。这些设置可以对所有的书生效，也可以只跟着某一本书。

**外援。** 后期剪视频时如果自己做不好，可以把活交给另一个会写代码的 agent。这不是工坊自己造的轮子，而是 DSH 官方的子智能体：装上 `@deepseek-ai/dsh-subagent-claude-code` 或 `@deepseek-ai/dsh-subagent-codex`，预设里已经挂好的 `@deepseek-ai/dsh-tool-subagent` 就会把 `subagent_claude_code` / `subagent_codex` 变成可用的工具——没装的时候，这两行什么也不做。

护栏在工具里，因为工具能检查提示词只能请求的事。收录书稿时：会删掉全书五分之一的清理模式被拒绝；无限回溯的正则三秒后被掐断；读起来像句子的"标题"会按编号分成两种，报告里附上可以直接照抄的修正；步数用尽的场记会留下它最好的一版切分。剪视频时：成片要过检查才收——有画面、有声音、不是静音、时长对得上讲述、没有大段黑屏；工作目录之外的路径交不上来。每个角色每次运行有步数上限，到了只剩交回工具还能用。

为什么文字模型只用 DSH 里配的？因为 agent loop 只认 DSH 的模型。让工坊自己再接一遍别家的文字接口，得到的是一批当不了 agent 的角色，和两处要各配一遍的模型。所以文字模型一律来自 DSH 的"设置 → 模型"，想用哪家就去那里接；工坊自己配的只有它特有的那几样：画图的、配音的、做检索的。（早先版本保存过"直连接口"的角色照常能用，只是只能普通调用，设置页会提示。）

为什么角色的模型要分开选？因为它们对模型的要求互相矛盾：

- **策划**要推理和发散（推演大纲、完善设定），温度偏高；
- **场记**要快、稳、读得细（收录、审校），输出是结构化的，温度很低；
- **导演**要快、守得住格式（脚本、分镜，幕间里你每动一下都在等它）；
- **后期**要写代码稳。

每个角色可以单独指定模型；不指定时，策划回落到写手，导演回落到写手或场记，都没配置就跟随会话模型。这样"只配一个模型也能用"和"每个环节都用最合适的模型"是同一套设置的两端。

还不是 agent 的：写手（有意如此，见上）；幕间的每一个回合仍是导演的一次调用——你每动一下都在等它，而且一场幕间本身就是一段连续的对话，更合适的形态是"一场幕间一个常驻的导演 agent"，这是下一步；插图的提示词、文风样段这类一句话进一句话出的小活。

总编被明确告知**不要自己"写"正文**：绕开写手流水线的正文，也就绕开了设定、人物此刻的状态和文风。但对话里有大量改动并不是"写"——作者口述了一句话、贴来自己写的一段、想把一个名字改对——让一个会重写的模型去做这些，慢、花钱、还不精确。所以总编有自己的一双手专门做这类事（`novel_edit`：替换、插入、追加、删除、整章换入），在三种情况下用：话是作者给的；改动是机械的；作者明确说"你来写"。

### 改书只有一条路

第一版用"禁令"划清总编和书的界线：用工具，别碰文件。真用起来有两个问题：总编能直接做的事太少；而它的工具不合手时，没有任何东西拦着它拿文件工具直接改——改完没有版本，记忆还在描述旧稿。用作者的话说，是主 Agent"偷偷暗改，但是和记忆、人设什么都不同步"。

解法不是更多禁令，而是一条足够宽的路：

- **每一种改动都有工具**，而且每个工具自己把账记全：旧稿存成版本，这一章的记忆重新收录，检索重建索引，结果里告诉总编这次改动牵到哪里——提到的人物的卡、后面已经写好的章节。记忆记错了可以直接改对（`novel_memory`），而不是指望再收录一遍能读对。
- **绕路的口子温和地关上。** 冲着一本书自己的文件去的 `write`、`edit`（或 shell 重定向）会被拒绝，并被告知该用哪个工具。这是作者的设置，不是总编的，可以放宽成"每次问我"或"放行"。
- **真绕过去了也看得见。** 工坊靠文件的实际状态（而不是时间差）分辨"自己写的"和"别人改的"；被编辑器、脚本或放行的工具改过的章节会记进改动记录、重新收录记忆，总编的上下文里也会写明发生过这件事。
- **没有任何改动是看不见的。** 总览页上有这本书的改动记录——总编用工具做了什么、在其他设备上做了什么、工坊之外改了什么——改过正文的可以一键撤销。

"Agent native"在这里落到实处就是：对话能做到屏幕能做的一切，而且它做的事和手在屏幕上做的一样看得见、一样能撤回。

## 三、写的时候记得什么

### 3.1 一本书就是一个目录

所有东西都落成文件：人写的是 Markdown（人物、世界观、文风、正文），结构和机器记忆是 JSON。理由有三个：作者应该能用任何编辑器打开自己的书；应该能用 git 管理；Agent 的文件工具在需要时也能读到它。代价是并发写入要小心——所有写入都经过同一个带锁的项目对象，并且监听目录变化，所以外部编辑也会实时反映到界面上。

### 3.2 人格系统

人物卡在小传之外有一块结构化的"人格"：带强度的特质、按优先级排列的价值观、说话习惯、绝不会做的事、压力下的反应。它存在的理由很具体——群像里人物"说话都一个味儿"几乎总是因为卡片只写了性格形容词。写手拿到的是可执行的约束（"她生气时话会变少"），而不是"她很内敛"。

同一张卡还带着人物的视觉锚点、人设图和配音设置。**形象和声音的一致性不靠模型记忆，靠每次调用都重复同一段锚点、带上同一张参考图（或同一段参考音）**——这是演出部分一切一致性的来源（见后文"全书一个样子"）。

### 3.3 群像：履历，不是标签

人物卡上**没有**"活跃 / 暂离 / 已死亡"这样的状态。最早是有的——一个词说完一个人在全书里的处境——后来去掉了，因为一本书不是一条直线：它有分出去的剧情线，也有写完后面再回头重写的前面。"已死亡"只对某一条线上某一章之后成立；写在卡片上，它在别的线上、在更早的章节里就是错的，而且它只强调"故事推进到了哪里"。

一个人在书里的处境是一份**履历**：哪一章登场，哪几章在场，哪里暂离，哪里回来，哪里离开或者死去。这份履历不需要另外保存——各章的收录里已经记着这一章有谁、他经历了什么、章末什么状态、是不是登场 / 离开 / 回归 / 死亡；沿着一条剧情线把它们排开，就是他的履历，因此永远和正文一致。沿着另一条线排开，是另一份履历：一个人在这条线上死了，在更早分出去的那条线上还活着。人物卡上另有一段"履历（一段话）"，由场记照着收录写、作者可以改。

收录会漏、会错，也有收录根本看不到的事（故事开始之前就已经去世的人）。所以作者可以**亲手记一笔**："在第 N 章登场 / 回归 / 离开 / 死亡"，或者"故事开始之前就已故 / 已离开"。它仍然不是标签：它是履历里的一件事，带着章节——在这一章所在的每条线上算数，不在的线上不算——并且盖过收录对那一章的说法。作者记下的死亡或离开，后面的章节里再提到这个人只算被提起；要让他回来，再记一笔"回归"。

写手每次看到什么，由它决定——按**正在写的这一章**、沿**这一章自己的那条线**：

- 所有人的卡片，哪一章都一样（这样请求的开头不随章节变，缓存才命中）：主角、配角是整张，其余一行；
- 本场人物（章纲列出的，加上从简报和上文里识别出的）：上一次出场结束时的状态 + 一两句原文台词；
- 一份"到这里为止，已经不在故事里的人"：已死亡的（可以被提起，不能再以活人身份出场）、已离开的（章纲没有安排就不要让他们回来）——只算**这一章之前**的章节。第十六章才死的人，对重写第五章的写手来说还活着。

出场记录同样来自收录，因此"谁已经十章没露面了"是算出来的，不是记出来的。界面上，所有人的履历排在一张表里（人物 → 履历表）：一行一个人，一列一章，沿选中的那条线读。

### 3.4 分层记忆与"收录"

"收录"是整个长篇能力的基础。每章写完，分析模型产出：

- 一句话梗概和几百字摘要；
- 硬事实（状态、关系、谁知道了什么、物品去向、世界规则、事件）；
- 每个在场人物的章末状态、所在地、情绪、学到了什么、一句有代表性的台词；
- 正文里新出现、设定里还没有的人物 / 地点 / 物品 / 势力 / 名词；
- 线索的埋设、推进与回收；读者此刻的疑问。

每十章再汇总成一段"篇章摘要"。于是远处的故事是粗粒度的，近处是细粒度的，最近几页是原文——这和人回忆一本书的方式一致。

记忆带着正文的哈希：正文一改，记忆即过期，界面和总编都会看到"未收录"的提示。

### 3.5 上下文打包：前情梗概 + 窗口里塞原文

写一章之前，模型读到的"此前的故事"分两层：

- **原文**：离这一章最近的若干**整章**，一字不差，按顺序排好。预算默认是所用模型上下文窗口的一半（一百万窗口的模型就是 50 万 token），也可以在设置里填一个数；按整章取，一章不会被从中间截断，放不下就不放。
- **梗概**：更早的章节，每章一行摘要（很早的章节十章并成一段"篇章摘要"）。没有收录过的章节用章纲里的梗概顶上——写过的章节不会有哪一章在上下文里毫无踪影。

这不是"装得下给全文、装不下就全换成检索"的二选一：稿子装得下时，梗概这一层是空的，就是全文；装不下时，近处是原文、远处是梗概，检索只负责从远处的章节里再捞几段相关的原文。窗口来自角色上自己填的值、DSH、接口，或一张常用模型族的对照表；谁都说不清的模型按 20 万算。

**下文也给。** 重写或修订中间的章节时，它后面已经写好的章节也一并给进去——由近及远、整章为单位，放不下的用梗概——并且明说：这一章必须接得上它们，不得与下文矛盾，也不要把下文的事提前写掉。前文的预算优先，下文至少保有三成。

**排列是为模型服务端的前缀缓存设计的。** 一次请求分成两段：

1. 不随章节变化的：作品信息 → 核心世界观 → 全书人物（主要人物全卡，其余一行）→ 前情梗概 → 前文原文。写下一章时，这一段只在**末尾**多出刚写完的那一章，前面的每一个字都不变。
2. 只属于这一次的：下文、本章人物此刻的状态、未回收的线索、相关设定、检索到的旧段落、下一章预告、本章已有正文、本章章纲、对这次写作的要求和篇幅。

为了让第一段真的稳定，做了三件事：写手的系统提示里不再带"这一章多少字""是不是续写"（挪到了第二段的末尾）；原文窗口的标题只写起点、不写终点；窗口**不逐章滑动**——它守着同一个起点直到放不下，然后一次放掉最老的四分之一，再守到下一次。所以连续写作时，绝大多数章节的请求都是"上一章的请求 + 一章新原文"，缓存命中的是几十万 token 里的绝大部分。模型服务端报告的缓存命中量记在用量账本里，写作结果里也会说这一次命中了多少。

检索本身是混合的：对中文按二元切分的 BM25，可选的向量检索，两者用倒数排名融合。不配置向量模型也能用。"只用检索"（最省）和"用满窗口"两种策略仍然可以在设置里强制。

### 3.6 文风

文风是独立于人物和世界的一份档案：视角、时态、基调、用词、节奏、意象、对白、必须做到的规则、禁用清单、范文。其中最有用的是禁用清单——"不要什么"比"要什么"更能约束模型。文风可以从范文里提炼，可以先试写一段再决定保存，一本书可以有多套并随时切换。

### 3.7 篇幅：可以给预算，也可以不给

一章可以有一个"建议字数"——章纲里填，或者给全书填一个默认值。它是建议，不是硬指标：写手被告知"约 N 字，上下浮动 15%"。

**不填，就由写手自己判断。** 这时它拿到的话是"没有规定字数：章纲里的每个节拍都写足、写透，不注水也不赶进度"，外加一句参考——这本书已经写好的章节平均多长。新建的书不再被悄悄盖上"每章 3000 字"；老书上那个没人选过的 3000（英文 2500）也不再算数。总编被明确告知：篇幅是作者的事，作者没说就不要自己编一个数。

### 3.8 剧情图：故事可以不止一条路

大纲里的分卷就是**主线**：这本书被阅读、导出、配音、搬上舞台的样子。主线之外可以有别的**剧情线**——策划推演出的另一种走向、幕间里演出来的一段、大纲被重写之前的旧安排。一条线从某一章之后**分出**，可以带着一句"分叉处的抉择"，走完自己的章节后可以**汇入**另一条线的某一章——于是剧情是一张图，而不是一根线。

- **重写大纲时，问的是"原来的怎么办"。** 推演章节可以指定从哪一章之后开始，并在三种做法里选一种：接着往后（追加）、**替换**那之后的大纲、或者**另开一条线**让两种走向并存。替换不会丢稿：被换下来的章节只要有一章写了正文，就整段留成一条"搁置"的线，随时能找回、能设回主线；一个字没写的才会被删掉。
- **线是可以摆弄的。** 在"大纲 → 剧情图"里：改名、写上抉择、让它汇入另一条线、搁置、删除，或者**设为主线**——它经过的章节成为正文的顺序，主线上被它替换的那一段自动变成一条线，分出和汇入的位置都对得上。
- **写下一章时选线。** 写作页一次列出一条线上的章节（它和别的线共有的部分变灰），可以切换；写完一章、故事在这里分了岔，页面会问"接下来写哪条线"。总编遇到同样的情况会先问作者。
- **线上的章节和别的章节一样。** 一样写、一样收录、一样审校、一样搬上舞台；它的"前文"是它自己这条线读下来的顺序，而不是主线。只有一点不同：**线上发生的事留在线上**——在一条支线里死掉的人，在书里并没有死；人物卡和主线的线索只跟着主线走。线被设为主线时，它的章节记忆才补记进设定。
- **幕间可以开成一条线。** 一场幕间除了"写成一章"接进主线，也可以"开成一条剧情线"：从它分出的那一章之后起一条新线，这一场是第一章，玩家的第一步就是那句抉择。
- **读的时候也能选。** 阅读页同样按线阅读；读到分叉的那一章结尾，下面不是"下一章"，而是几条路——每条路上写的正是分叉处的抉择。这是把故事做成"可以选的"的那一步：图、抉择、每条路上的章节，都已经在数据里。

## 四、怎么改：同一套提案机制的五种粒度

| 作者心里的模式 | 实际发生的事 |
|---|---|
| 大纲推演 | 架构模型读记忆与线索，给出后续章纲 / 节拍 / 假设分支；先看方案，再决定是否写入大纲 |
| 局部修改 | 选中一段 → 写手只重写这一段（带着前后文），生成提案 |
| 整章修改 | 写手按一条指令重写整章，生成提案 |
| 全文修改 | 架构模型先判断哪些章受影响（分诊），写手只改这些章，每章一个提案，归为一批 |
| 世界观修改 / 人物修改 | 先改设定，再用"把这条变更同步到正文"发起一次全文修改 |

几条共同的规则：

- **改动先是提案。** 提案带差异对比，采纳才生效。界面发起的修订总是提案；总编发起的默认直接生效（它在对话里向你汇报），也可以在设置里改成"先作为提案"。
- **生效前先存快照。** AI 写作、修订、恢复之前都会给旧稿留一份版本，可以对比和恢复。
- **提案会过期。** 片段提案记录的是"被替换的原文"；原文后来被改过，提案就无法应用，只能放弃重来——宁可这样，也不要把改写贴错地方。
- **只读会话要先问。** 会话处于只读权限时，所有会写文件或花钱的工具调用都会先征求同意。

**导入**是"反向的收录"：拆章 → 逐章收录 → 把收录到的人物片段归并成人物卡、把实体归并成世界观条目 → 由章节摘要重建大纲和线索 → 从正文提炼文风。它复用的就是平时写作后那套记忆流水线，所以导入的书和从零写的书在工坊里没有区别。

## 五、怎么看、怎么动手：工坊

界面有两个入口，是同一棵组件树：

- **左侧栏的页面**：全局的书架和书，不需要会话；
- **会话右侧栏的标签页**：绑定这个会话，书和对话并排。

第二种形态是"深度融合"的关键：总编调用写手时，章节会流式出现在旁边的编辑器里；你在正文里选中一段，可以直接让写手改，也可以"和总编讨论"——选区会带着章节信息落进对话输入框。对话里每一次 `novel_*` 调用都显示成一行"让哪个模型做了什么"，点一下就跳到工坊对应的位置。

八个视图各管一件事：总览（下一步该做什么）、人物（人物卡连同履历表、关系、龙套——和人有关的只有这一页）、设定（世界观、文风、画风）、大纲、写作、阅读、审校、演出。几条贯穿的原则：

- **先告诉作者下一步。** 总览页不是仪表盘，是待办：哪章没收录、下一章能不能写、有多少提案在等。
- **圈定即操作。** 修改的入口是"选中文字"，而不是先进入某个模式再找位置。
- **AI 的产出默认是建议。** 设定建议、修订提案、推演方案，都要经过你点头。
- **长任务可见、可停。** 写作、导入、合成都是后台任务，有进度和流式文本，能随时停止；停止一次写作会保留已经写出的部分（前提是它没有覆盖别的东西）。
- **窄处也能用。** 标签页常常只有四五百像素宽，布局按容器宽度而不是窗口宽度切换。

### 看的页面，按"一款很美的游戏"来做

这个东西说是创作工具，更多的是让创作者**欣赏**自己作品的东西：很多人的爱好就是翻人物设定、翻世界设定。所以"好看"在这里是功能要求，不是点缀。凡是用来看的页面——阅读、听、有声漫、人物、地点与物品、世界观、主页——以"一款很美的游戏"为标准：画面大、有图就把图放在最显眼的地方、能点进去逛（从一座城到一户人家到一个人）、转场和动效恰到好处，而不是表格和表单。编辑功能一个不少，但收在"编辑 / 制作"后面：平常看到的是成品，要动手时再打开工具。同一样东西的"看"和"改"是一个地址的两面，从哪一面都能一步到另一面。

**"观看"是一个应用，三处用。** 读者看到的东西——正文（读 / 听 / 看有声漫）、人物、世界——是一套页面（`client/reader/`），吃的是后台同一处产出的回答（`core/reader.ts`）。它出现在三个地方：工坊导航里的"观看"、发给手机的阅读页、发布出去的网站。所以不存在"工坊里一个样、发出去另一个样"。三处只有两点不同：作者自己的"观看"里也有正文还没写到的人和地方（那是计划，不给读者）；作者那边每一页右上角多一个"编辑"，一步到这样东西的编辑页，编辑页上的"观看"一步回来。给读者的人物页只带设定集会印的东西；动机、缺陷、弧光、秘密、备注和"怎么写 / 怎么画 / 怎么配音"留在作者这边。

### 一键与批量

一件事对一章做一次是按钮，对五十章做五十次就是折磨。所以凡是"对很多章 / 很多人 / 很多地方做同样的事"，都是**一个任务**：

- **演出 → 一键制作**：一张表列出每一章的进度（脚本、配音、声音、分镜、画面、成片），勾上要做的步骤和章节，点一次。每一章的脚本排好之后，它的配音、声音和分镜同时进行，分镜出来再画画面，都齐了才剪成片；几章同时在流水线上走，先开始的先做完。
- **写作 → 批量写作**：一章接一章地写——没有节拍的先推演节拍，写完一章收录一章，下一章才动笔，所以每一章都读过上一章刚写下的东西。不写作时，节拍、收录、审校可以对很多章同时做。
- **插图 → 批量绘制**：人设图和场景设定图先画，立绘、章节插图和封面等它们画完再照着画；每个人的专属声线也可以一起做。
- 单章的页面上也有一键：听书页的"一键生成有声版"是脚本 + 配音 + 声音，有声漫页的"一键制作这一章"是全套。

批量任务有三条规矩。**只补缺的**：每一步动手前先看还有没有要做的，所以中途停下、或者有几步失败，再点一次只做剩下的。**失败只坏自己**：某一章的某一步失败，这一章后面依赖它的步骤不再开始，别的章照常；任务结束时逐条列出没做成的和原因。**都看得见**：每一章每一步的状态在一张表里实时更新，角色 agent 的运行照常挂在对话的子智能体列表里。总编用 `novel_batch` 做同样的事。

**并发是另一回事，而且只有一处。** 同时发出多少个请求，不由某个任务决定，而由四道"闸门"决定：语音、图片、声音、文字各一道，不管是哪一章、哪个任务在用都算在一起。默认 8，最多 256，在设置里改。服务回答"太快了"时，闸门自己降速（减半、停一停），把被拒的请求重发而不是丢掉，通顺之后一步步升回去，期间界面上明说"语音服务在限流：8 → 4"。所以数字可以放心往大了填——真正的上限是账号在那个服务上的限额，它是撞出来的，不是猜出来的。

### 对话优先：页面是给人看和细调的

这是一个 agent 原生的应用，所以最直接的用法不是点页面，而是在会话里和总编说话。为此定了三条：

- **页面能做的，对话里都能做。** 每个页面背后的操作都有对应的工具，包括设置（`novel_settings`：查看与修改模型分工、一键配置某个服务、改作品信息）和那些零碎的手工调整（`novel_manage`：恢复历史版本、改一句台词、改一格分镜、处理审校问题……）。页面不是功能的唯一入口，而是**让人看见、核对、细调**的地方。
- **总编可以把页面打开给你看。** `novel_show` 让总编在作者的窗口里打开某个页面、某一章、演出页的某个标签——"打开大纲给我看"就真的打开了，而不是告诉你去哪里点。工坊在总编第一次开工时自己出现在对话右侧；之后要不要留着由作者决定。
- **全屏用宿主自己的。** 右侧栏本来就有全屏模式，工坊只是在自己的顶栏放了同一个开关，离作者的视线近一点。不另做一套覆盖层，状态也就不会有两份。

唯一不走对话的是密钥：总编不接收也不复述任何密钥，需要时把设置页打开，让作者自己贴进去。

### 一场对话，一本当前的书

一个工作区里可以有好几本书。对话和旁边的工坊不能各自以为"说的是哪一本"，所以只有一个事实——**这场会话当前的书**——两边都读它、都写它。

- **在工坊里换书，对话跟着换。** 另一种做法是让面板可以看 A、总编却在 B 上干活，那样每一句"接着写下一章"都有歧义。所以"看哪本"就是"换到哪本"，换的时候工坊会明说。
- **总编必须被明确、持久地告知。** Harness 会把变化了的运行时上下文作为一条消息写进对话自己的历史，所以换书这件事就记在之前那些对话旁边：现在是哪本、之前谈的是哪本、上一本没做完的事要点名去做而不是带过来。它随每次摘要重述，压缩上下文之后也还在。
- **一次调用作用于"模型最后被告知的那本书"**，而不是执行那一瞬间恰好在用的那本。作者在总编干到一半时换了书，并没有改变它已经决定要做的那几步；下一步它会被告知，再重新决定。
- **替对话干活的 agent，站在它干的那本书上**——而不是它所在的文件夹恰好是哪本书。角色的一次运行、总编派出去的子智能体，都是一场新的对话，文件夹是从上级对话那里继承来的；而一个文件夹可以自己是一本书、里面又放着别的书（在空工作区里建的第一本书就是文件夹本身，后来的书放在它里面）。所以对子对话，文件夹排在最后问：先看它的任务点名的那本书，再看它为之干活的那场对话的书。先问文件夹的话，停在场记旁边的工坊会打开外面那本书，派出去的帮手也会被告知错的书。
- **一场对话操作多本书仍然可以**——靠点名，不靠猜。每个工具都可以带 `book`；对话里的工具行会标出来；一场对话换过书之后，每条结果都写明是哪本书的。总编主动去改会话工作区之外的书，要先问一句。

### 不许静悄悄地失败

大多数按钮只是发起一个任务就返回。没人等着的任务失败了，也得让作者知道——尤其不能在"根本没配置"的时候一声不吭。两条规则：凡是这个工坊亲眼看着启动的任务，结束时都要有交代；意味着"还没配置"的失败——没有语音模型、缺密钥、订阅没登录——不显示成一条报错，而是一个带出路的提示：一键配置，或者直接打开设置里对应的那一节。长任务要说清自己在干什么：合成一章语音时，显示已完成几句、正在念哪一句、已用多久、大约还要多久。

半秒钟的事也一样。按下去的按钮在活干完之前一直写着它正在做什么；工坊底部有一条"进行中"，列出这本书此刻在跑的每一件事——Host 还没回话的请求，和不管谁发起的任务——各自在做什么、做了多久、怎么停。"点了没反应"就是缺陷，不管背后的代码当时在忙什么。

打了折扣的结果也一样。某一步没能把活干好、退而求其次了——比如模型的回复被截断，有声脚本的某一段只好按规则切——就把这件事连同原因写进它产出的东西里，页面上照实显示。工坊也不再给模型的回复长度设自己的上限：会思考的模型，思考和回答花的是同一份额度，按"回答该有多长"定的上限会把回答悄悄截掉。就是这一个错，造出过认不出说话人的脚本和只有两格的分镜，而且看起来都像做完了。

### 接上模型：一键与逐项

配置同时照顾两种人。**不想研究的**：第一次打开工坊，如果什么都没配过，会先到"先把模型接上"这一页——选一个服务、贴一个 key、点一下，写作、插图、配音、检索按推荐配好；密钥先向服务验证，验证不过就什么都不改。**想自己定的**：每一项（四个角色、插图、配音、检索）都能单独指定服务、接口地址、密钥、模型和思考强度；文本角色既可以用 Harness 里配好的模型，也可以直接指向任何 OpenAI 兼容接口。

密钥按**接口域名**保存，一个域名一条记录，存在 Harness 的凭据库里。这样同一家服务的几项能力填一次就够；密钥也只会发给它所属的那个域名——把某一项的地址改到别处，密钥不会跟过去。

**推荐什么是数据，而且是发布出来的。**模型更新得比代码发版快：一家服务用哪个图像模型最合适、模型栏旁边值得列出哪些候选、一个模型族的窗口有多大，都是按月过时的东西。这些一个都不写在代码里，而是 `recommended.json`——带期号和日期，随每个版本一起发布。作者的设置跟不跟它走，由作者定：仍然是上一期推荐值的设置换成新一期的推荐，作者自己选的一概不动；换了什么都会说清楚——旧值、新值，以及一个"改回去"。不跟随的作者只会被告知这一期会改什么，什么都不改。一个模型被取代这件事，从不悄悄发生。

**设置页一开始是短的。**只选两个模型——写手的，和班底共用的——插图、配音、声音、检索各占一行。一个角色除了模型之外能被交代的一切，都在"高级选项"里这个角色自己的那一块上：它怎么干活、能用什么工具、最多几步，不再是页面另一处的第二张表。

ChatGPT 订阅是个特例：它能画图，但没有 API key。工坊不为它另做登录，而是借用已经存在的登录——Codex Connect 插件暴露给伴生插件的出图服务，或者本机已经登录的 Codex CLI。订阅里没有向量和语音接口，这两项如实标注为"需要别的服务"。

## 六、写完还能变成什么：演出

五件事共用一个数据模型，枢纽是**有声脚本**：

```
正文 ──导演──▶ 有声脚本（逐句：旁白/对白/心声、说话人、表演提示；逐场：环境音）
                 │
                 ├──语音合成──▶ 有声剧（每句一段音频，按人物固定音色）
                 │
                 └──导演──▶ 分镜 ──绘图──▶ 有声漫（每格画面对应若干句台词 + 镜头运动）
                                              │
                        配音 + 音效 + 画面 ──后期──▶ 成片（一个 MP4）
```

- **有声剧。** 说话人的声音按固定顺序决定：人物卡指定的音色 → 为他设计的专属声线 → 按性别年龄选角。选出来的声音写进这本书的**声音表**，以后都从表里读，所以选角不再取决于"这一章谁先开口"，没有人物卡的路人也有一个固定的声音。每句的合成结果按"服务 + 音色 + 表演提示 + 文本"的哈希缓存，所以改三句台词只重新合成三句。语音服务是可插拔的接口。
- **不靠耳朵的"听检"。** 生成式语音模型并不总是照做：一句话回来换了个嗓子、只念了一半、或者比上一句响一倍——而且越短的句子越不稳。所以管线对每一次合成都量一量：时长配不配得上字数、音量多大、音高的中位数和这个声音的参考音（或它自己的长句）差多远；不合格就重念，留下最好的一次，仍然突出的标出来，最后把所有留下的句子拉到同一个音量。脚本那边也配合：旁白整段成行，不切成碎片；表演提示不必每句翻新。这一切不需要再调一个模型，也不声称量不出来的东西：一两个字的句子，音高说明的是声调而不是说话的人，所以极短的句子不按音高判。
- **环境音。** 不调用任何模型，由浏览器用 Web Audio 实时合成：滤波噪声做底，慢速调制做"呼吸"，再加上定时的一次性声音（雷、柴火噼啪、水滴、虫鸣）。脚本里只需要标"这一场是雨夜"，零成本、零素材。
- **有声漫。** 脚本先切成"镜头单位"——短句整句算一个，长句按句子拆——分镜导演把单位编成一格格画面，所以半分钟的旁白中途也能换画面。切多少格由作者定（用"一张图停多久"来表达的密度，或者交给导演，再加一个永远算数的上限），因为每一格都是一张要花钱画的图。整章分窗口交给导演；导演中途停了，就把剩下的再问一遍，而不是让最后一格盖住后面所有的内容。提示词里自动带上出场人物的视觉锚点和全书的画风，并把出场人物的人设图当参考图。播放时按台词推进，画面做缓慢的推拉摇移。
- **成片。** 有声漫是工坊边放边拼出来的；成片是一个文件，而它**不是按规则拼的**。这一章已经做好的东西——每一句的配音、声音提示、每一格的画面——都只是素材：工坊把它们排在一条时间线上（每句的起止秒数、每格画面的起止、每处声音的落点），连同命令行顺手的几种形式（一条已经对齐的整轨配音、按句切好的字幕、分镜表、一份能直接跑出朴素第一版的基础脚本）交给**后期 agent**。怎么剪是它的事：读素材、看这台电脑的 ffmpeg 能做什么、写自己的脚本、跑、检查、再改；做不好就叫外援。工坊留给自己的只有验收：有画面、有声音、不是静音、时长对得上讲述、没有大段黑屏、观众看得到台词，过了才收。字幕正好说明这条线划在哪里：工坊给出切好、对好时间的台词，说明“观众必须看得到”，检查它们确实在画面里或作为字幕轨带在文件里——但不自己写工具去放。第一次剪回来的成片只带了一条字幕轨（这台电脑的 ffmpeg 画不了字），最顺手的修法是工坊自带一个画字的本机小程序。作者从两点否了它，这两点现在是规矩：**agent 能干的活，不用确定性的小工具替它干**——素材、说清楚要什么、验收是工坊的事，用什么命令是 agent 的事；**插件不绑定任何系统，而 agent 不受任何限制**——插件要跑在 DSH 跑的每一种系统上，所以不带只属于某个系统的代码；干活的 agent 面对的只有眼前这一台电脑，这台电脑上有什么它都可以用。
- **幕间。** 见下一节。

### 读和听是同一页

有声剧原先是"演出"里的一个标签页，和阅读器分开。但听就是用耳朵读：还是那一章，听的人想在屏幕上看到的是正文，不是一张逐句的录音表。所以听就在阅读器里——有声漫也是同一章、同一份脚本，所以看也在这里。阅读器有三种版面（文字、逐句的脚本、有声漫），前两种底下是同一个播放条："听"不是一种模式而是一个按钮，无论开着哪种版面，这一章都停在同一处。在正文上听的时候：脚本的每一句在正文里定位（脚本不管分段，对白也没了引号，所以匹配时不看空白，找不到原样就按这句话怎么开头、怎么结尾来定位），正在念的那句亮起来，点任何一句就从那里开始播。作者的工具——生成、听检并补合成、导出、逐句的脚本——放在同一页的上方，而不是另一个页面。

手机上看到的也是这一页。给别的设备用的阅读器不能是 Harness 本身（它留在这台机器上，守着自己的认证），所以插件为它另起一个很小的服务：不开就不存在，逐本开启；从构造上就是只读的（没有任何能写、能碰到模型、密钥或未分享的书的路由）；地址里带一段可以更换的随机口令。它用的就是工坊阅读器的那些组件，所以两边不会各走各的。

### 全书一个样子，而且不藏着

一张图一条提示词地去配图，会出两种毛病。一是词在绘图模型那里是另一个意思——书里的"教会"被画成欧式教堂，"白甲"被画成十字军；二是模型没见过这个人，每次都画一个新的人。而常见的补救往往是藏起来的：一句悄悄接在提示词末尾的风格短语，决定了全书的视觉基调，却从不给作者看。

所以一本书的样子由作者读得到的几个部分组成，每张图都记着自己用了哪些：

- 每本书一份**画风**，而且只属于书：民国悬疑和太空歌剧不该是同一种画法，所以画风是这本书“设定”里的一页，不是工坊的一项设置。它由导演按这本书自己来定——时代与地域、文字的气质、主要人物——导入书稿、起草设定时各定一次，作者随时可以让他重定。以前的书如果还没有自己的画风，从内置默认（或以前填过的全局画风）起步，并且第一张图就把这段文字写进书的 `novel.json`，连同来源一起显示出来，随时可改。会决定一切的默认值，必须落在明处；
- **"不要出现"清单**——工坊、作品、人物、单次调用四层——写这个世界里没有的东西。它既作为负面提示词发给绘图模型，也交给写画面描述的模型，后者还被要求把带歧义的专有名词换成它在故事里实际的样子；
- 每个人物一条**视觉锚点**：把人物卡上的散文外貌一次性提炼成绘图模型每次都画得一样的短语，之后每张有此人的图都原样带上。导演写它的时候手里拿着画风。画风能说的不止"怎么画"——"服饰、建筑是明制"——而它接在画面内容后面，只能给已经写明的东西上色：锚点照原文写了"总编一根大辫"，换什么画风画出来都是辫子。所以作者定下的年代和形制要写**进锚点里**，写锚点的人也要被告知：形制以画风为准，压过原文——是换掉，不是两样都留；这个人自己的东西（颜色、纹样、材质、随身的物件）带到新的款式上；
- **人设图**：同一个人的正面、侧面、背面，之后每张有此人的图都把它当参考图。多套服饰是"造型"，各自的人设图从主人设图衍生——同一张脸换一身衣服；常去的地点也有自己的场景设定图。

顺序很重要，工坊也会这样提示：先定画风和禁画清单，再做锚点和人设图，最后才配图。

**文字在前，图在后。** 参考图是一条提示词里分量最重的东西：告诉绘图模型"要和它一致"，它就把参考图原样还回来。所以参考图往哪个方向传，是要定下来的事，而且只有一个方向——从文字到人设图，从人设图到其他所有图。主人设图只照视觉锚点和画风画，永远不照这个人的任何旧图：照着上一张人设图去画人设图，它就永远变不了，不管作者改了什么，而且屏幕上没有任何地方说明为什么。立绘、插图、分镜画面照人设图画；造型照主人设图画，并且在提示词里写明参考图是用来干什么的（要的是脸，不是那身衣服）。想让一个人变样：改文字，重画人设图——之后，照着旧人设图画出来的那些图会自己说明。

**每张图都追得到来历。** "每张图都记着自己用了哪些"值多少，要看图画歪了的时候作者能拿它做什么。点开一张图，旁边就是它的记录：提示词按发出去的先后拆成的每一部分、各自在哪里改；随提示词一起发出去的参考图——每一张都能再点开看它自己的记录，一个长相可以顺着图一张张追回去；发给绘图模型的原话，一字不差；以及这一切和现在的书对照起来怎么样（锚点或画风在这之后改过；立绘是照着一张已经重画过的人设图画的）。于是一条没人要的辫子，要么是锚点里的一个词，要么是一张被带上的图，要么是模型自己的习惯——作者不用问任何人就分得清。

### 花了多少

演出是花钱的地方，一百万上下文的写手模型也不便宜。工坊给自己发出的每一次模型调用记账——各角色的 token、图片张数、语音秒数——按模型、分工、作品、日期汇总。它只计数，不猜价格：作者填了单价的模型才显示金额，用作者填的货币；没填的如实标"未定价"。对话里总编自己的那部分由 Harness 统计，账本会明说这一项不在其中。

### 幕间：为什么不做成"酒馆"

角色扮演工具的核心是"和角色聊天"，故事是聊天的副产品。这里反过来：**故事是主体，扮演是探查故事的一种手段**——在写一场对峙之前先下场演一遍，看看人物会怎么反应；或者试一个"如果当时她没走"的岔路。

所以幕间被设计成正史上的一个"岔口"：

- 它锚定在某一章之后，导演模型只知道到那一章为止的正史；
- 你可以扮演其中一个人物，也可以只当导演，发出"门外有人敲门"这样的场面指令；
- 导演每回合给出旁白、各人物的台词与动作、可选的选项、场景变化（地点、时间、氛围、环境音）和它在跟踪的变量；
- 界面按视觉小说的方式呈现：背景、立绘、对话框、选项、配音、环境音——图像和语音都是按需生成的，所以它确实是一部"现场生成的 Galgame"；
- 结束时有三种去向：作废（不算数）、留作番外、或者让写手按本书文风把它**改写成一章**并入正史。只有最后一种会改变正史，而且之后同样要收录。

## 七、与 Harness 的融合方式

- **一个 npm 包，三个入口。** 宿主端（项目、流水线、任务、接口）、Agent 端（工具、提示词、指令，挂在预设里）、浏览器端（工坊）。包自带一份配置补丁，安装即生效。
- **只走官方接缝。** 文字模型调用走 DSH 的模型运行时，"设置 → 模型"里配置的每条线路都可用；角色作为 agent 运行走 `ctx.subagents`（插件注册自己的 provider）；外援走 DSH 自己的 `dsh-tool-subagent`；密钥走凭据库；界面通过槽位注册到左侧栏、右侧栏和工具行；浏览器与宿主之间走 DSH 自己的连接（一条带鉴权的接口），所以 Web 和桌面版行为一致。
- **Harness 给自家 agent 的，插件自己的调用拿不到。** 失败请求的重试由 `dsh-llm-retry` 挂在 agent loop 上；通过 `ctx.llm.stream` 发出的调用，第一次失败就是最终失败。所以工坊对仍然是"调用"的那些调用自己执行供应商的重试策略，并把不止是一次调用的工作搬到 agent loop 上——在那里这些都不需要第二份实现。
- **提示词分两层。** 一段不变的分工说明进入系统提示（可以被前缀缓存）；项目摘要和当前工作模式作为动态上下文，只有变化时才重新发送。
- **工作模式是会话状态。** 构思 / 设定 / 大纲 / 写作 / 修订 / 审校 / 演出 / 幕间，可以在工坊右上角切换，也可以让总编切换；它改变的只是总编此刻的规则。

### 加密的书

书是普通文件，所以谁都能读；加密的书，是作者不想让任何东西读到的书——备份、云盘同步、随手打开这个文件夹的人。只加密"正文"是不够的：一张立绘、一句配好的台词、一份记忆摘要、一个人物文件的文件名，透露的并不比正文少。所以加密做在所有东西的下面：对一本书的每一次读写都经过同一个很小的接口，加密的书在这个接口里把内容和文件名一起加密，其余代码既不知道也不关心。

**关于这本书的对话也要锁。** DSH 把每一段对话存成磁盘上的一份日志，谁能读磁盘谁就能读；而和总编聊这本书的对话里就有这本书——它读过的章节、作者口述的情节、各个角色查到的东西。DSH 没有加密或删除一段对话的接口，所以工坊在书上锁时把这些对话从 DSH 手里**拿走**：每一份日志加密后放进工坊自己的目录，明文从 DSH 的会话库里删掉（连同 DSH 从中算出来的标题、摘要缓存）；书解锁时原样放回，对话可以接着聊。哪些对话算"关于这本书"：绑定到它的对话、总编的工具碰过它的对话、各个角色为它跑的记录，以及这些对话的所有子对话。为了在书**锁着**的时候也能把对话收进去（比如上锁那一刻还开着的对话，要等它关闭），加密书的 `novel.json` 里带一把只进不出的公钥：谁都能往里放，只有书的钥匙能取出来。正在使用的对话不会被强行拿走，它在被释放后、最晚在下次启动 DSH 时加密；明文只有在加密副本落盘（钥匙在手时还要解开比对一遍）之后才删除。

书的钥匙是随机的，未包裹的形态只存在于运行中的 Harness 的内存里。落在磁盘上的，是按"每一种开锁方式"各包一份的钥匙——密码、这台电脑的系统解锁、输过一次密码的设备——存在唯一保持可读的那个文件里。"是不是本人"交给操作系统去问（触控 ID、Windows Hello、电脑密码）：通过系统自带的脚本宿主——Mac 上是 `osascript`，Windows 上是 PowerShell——用几行脚本去问，它只回答是或否，手里没有任何秘密；它守着的那份秘密放在系统账户的凭据库里。为此不编译、也不随包带任何本机程序：DSH 跑在哪里，插件都是同一份文件；系统没有这种确认的地方（目前是 Linux），书就只用密码打开。DSH 自己没有可供插件调用的"机主确认"——桌面版的外壳没有开放，外壳里的网页也用不了 WebAuthn（浏览器只允许 https 和 localhost）——否则工坊会直接用它。总编被设计在这一切之外：它能把书锁上，永远不能解锁，密码也永远不在对话里输入。

## 八、有意没做的事

- **不做协作编辑。** 一本书一个作者；多人同时改同一章不在目标内。
- **手机阅读不做传输加密。** 它是局域网里的明文 HTTP，界面上也照实说——一张手机肯信任的证书，不是一个插件变得出来的。
- **不内置任何模型或密钥。** 一切模型能力来自你在 Harness 里的配置。
- **不调用视频生成模型。** 成片是后期 agent 用已经做好的配音和画面剪出来的；有声漫是"会动的分镜"。让画面自己动起来的模型不在这一版里。
- **正文编辑器保持朴素。** 它是一个文本框而不是富文本编辑器：章节文件必须是你在任何地方都能打开的纯文本。
